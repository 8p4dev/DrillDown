# 1부. 이해하기

## 1. 한눈에 보기

### 무엇을 하는 앱인가

Drill Down은 **지식을 트리로 정리하고, 그 트리를 외우는** 학습 웹앱이다.

보통의 플래시카드는 "단어 → 뜻"이 일대일이다. Drill Down은 개념 하나가 여러 하위 개념으로 뻗는 트리를 만든다. 그리고 위에서 아래로, 전체 구조를 먼저 떠올린 뒤 세부를 채우는 방식으로 외우게 한다. "드릴 다운"은 상위 개념만 보이다가 누르면 하위가 차례로 열리는 방식을 가리킨다.

트리의 항목 하나를 **노드**라고 부른다. 화면에는 노드가 네모난 **카드**로 그려진다. 이 문서에서 "카드"는 항상 "화면에 그려진 노드 한 장"을 뜻한다.

사용자가 하는 일은 두 가지다.

1. **만들기**: 편집기에서 트리를 만든다. 노드에는 짧은 제목과 내용이 있다.
2. **외우기**: 같은 트리를 세 가지 학습 모드로 푼다. 푼 결과에 따라 간격 반복 알고리즘(FSRS)이 다음 복습 날짜를 정하고, 그날이 되면 "오늘의 복습"에 다시 나온다.

| 화면 | 주소 | 하는 일 |
|---|---|---|
| 내 트리 | `#/` | 트리 목록, 만들기, 이름 변경, 삭제 |
| 편집 | `#/tree/<id>` | 카드 그래프로 트리를 편집 |
| 플래시카드 | `#/tree/<id>/flash` | 개념을 보고 하위 개념을 떠올린 뒤 [알음]/[모름] |
| 빈칸 | `#/tree/<id>/dnd` | 뼈대만 남은 트리의 빈칸에 카드를 끌어다 놓기 |
| 백지 | `#/tree/<id>/blank` | 루트만 남은 화면에서 트리 전체를 다시 조립 |
| 오늘의 복습 | `#/review` | 복습할 날이 된 항목만 모아서 풀기 |
| 공유 보기 | `/t/<slug>` | 남의 트리를 읽고, 체험 학습하고, 내 트리로 복제 |
| 갤러리 | `#/gallery` | 공개된 트리 목록 |
| 계정 / 관리 | `#/account`, `#/admin` | 프로필, 휴지통, 내보내기 / 운영 도구 |

### 아키텍처 세 문장

1. **브라우저가 주인이다.** 내 트리와 학습 기록은 먼저 브라우저 안의 저장소(IndexedDB)에 저장된다. 로그인하지 않아도 편집과 학습이 전부 된다.
2. **서버는 복사본을 맡는다.** 로그인하면 변경분을 서버로 올리고(push) 다른 기기의 변경을 받아온다(pull). 서버는 그 밖에 로그인, 공유 링크, 갤러리, 관리 기능을 담당한다.
3. **서버는 프로세스 하나다.** Node 프로세스 하나가 API, 공유 링크용 HTML, 빌드된 클라이언트 파일을 모두 내보낸다. DB는 SQLite 파일 하나다.

### 전체 그림

```
[ 브라우저 ]

  화면  src/features/        editor · flash · dnd · share · account · admin
    │
    ├─ (가) 내 트리와 학습 기록을 읽고 쓸 때
    │       ▼
    │     저장 계층  src/core/repo.ts
    │       ▼
    │     IndexedDB   trees · nodes · srs        ← 여기가 "진실"
    │                 outbox · meta              ← 동기화용 장부
    │       ▼
    │     동기화 엔진  src/core/sync/engine.ts    (로그인한 기기에서만 동작)
    │       │
    │       │  POST /api/sync (push)    GET /api/sync?since=N (pull)
    │       ▼
    └─ (나) 로그인, 공유, 갤러리, 관리처럼 서버에 직접 물을 때
            │  src/core/api.ts
            ▼
[ Node 서버 ]  Hono, 프로세스 하나

  /api/*       server/account/   로그인(OAuth) · 계정 · 관리자
               server/sync/      동기화 · 공유 · 갤러리
  /t/<slug>    공유 링크용 HTML (미리보기 정보를 넣어서 응답)
  그 외 주소    dist/ (빌드된 클라이언트) 를 그대로 내보냄
    ▼
  SQLite       data/app.db
```

그림에 나온 말 다섯 개만 먼저 풀어 둔다. 자세한 설명은 뒤 장에 있다.

| 말 | 뜻 |
|---|---|
| IndexedDB | 브라우저에 내장된 데이터베이스. 사이트마다 따로 있고 오프라인에서도 쓸 수 있다 |
| outbox | "서버로 아직 안 올린 변경" 목록. 무엇이 바뀌었는지만 적는다 |
| push / pull | 내 변경을 서버로 올리기 / 다른 기기의 변경을 서버에서 받기 |
| srs | 노드별 학습 기록 테이블 (언제 다시 복습할지) |
| slug | 공유 링크에 들어가는 11자 토큰 |

### 지금 상태

- **기능은 구현돼 있다.** 편집, 학습 모드 세 가지, 복습, 로그인, 동기화, 공유, 갤러리, 관리자 화면까지 있다. 브라우저 통합 테스트 20개가 전부 통과한 기록이 있다 (`docs/plans/orchestration_p2.md`).
- **코드가 이 PC에만 있다.** `app` 저장소에는 원격(remote)이 설정돼 있지 않다. 디스크가 망가지면 복구할 곳이 없다.
- **실제 환경에서는 검증되지 않았다.** 실제 Google·카카오 로그인 왕복, iOS·Android 실기기, 카카오톡 인앱 브라우저, Raspberry Pi에서의 구동이 미검증으로 기록돼 있다 (`docs/plans/orchestration_server.md`).
- **운영 배포는 준비물만 있다.** Raspberry Pi 한 대와 Cloudflare Tunnel로 운영하는 것을 전제로 설정 파일과 절차서가 있다 (`deploy/`, `docs/ops/runbook.md`). 실제로 배포돼 있는지는 코드만으로는 알 수 없다.

직접 띄워 보려면 [11장의 "처음 실행하기"](#처음-실행하기)를 보면 된다. 명령 두세 개로 된다.

## 2. 폴더 지도

`C:\drilldown` 아래에는 폴더가 둘 있다. `drilldown-biz`는 사업 검토 문서 묶음이고 코드가 아니다. **실제 웹앱은 `app` 폴더이고, 독립된 git 저장소다.** 이 문서는 `app` 이야기다. 바깥 저장소와의 관계는 [16장](#16-저장소-구성-개발-방식-연혁-docs-지도)에 있다.

```
app/
├─ index.html            진입 HTML. 테마를 첫 화면 전에 적용하는 인라인 스크립트 포함
├─ src/                  클라이언트 (브라우저에서 실행)
│  ├─ main.tsx           React 시작점 (10줄)
│  ├─ App.tsx            앱 틀: 상단 바, 화면 고르기, 알림
│  ├─ router.ts          주소 → 화면 변환 (직접 만든 라우터)
│  ├─ index.css          디자인 토큰과 공용 스타일
│  ├─ core/              화면이 없는 로직과 저장
│  │  ├─ types.ts        데이터 타입과 저장 한도 CAP
│  │  ├─ db.ts           IndexedDB 스키마, outbox 기록 함수 track()
│  │  ├─ repo.ts         트리·노드 읽기/쓰기
│  │  ├─ sync.ts         동기화의 얇은 창구 (첫 화면에 실리므로 작게 유지)
│  │  ├─ sync/engine.ts  동기화 엔진 본체 (560줄. 로그인했을 때만 내려받는다)
│  │  ├─ api.ts          서버 호출 함수 하나와 응답 타입
│  │  ├─ me.ts           로그인 상태
│  │  ├─ srs/index.ts    간격 반복: 채점 → 다음 복습 날짜, 색 판정
│  │  ├─ outline.ts      들여쓰기 텍스트 ↔ 노드 변환
│  │  ├─ backup.ts       백업 파일 검사와 가져오기
│  │  ├─ source.ts       학습 화면이 데이터를 읽는 창구 (StudySource)
│  │  ├─ events.ts       사용 이벤트를 로컬 events 테이블에 적는 함수
│  │  └─ path.ts, inapp.ts, avatar.ts   작은 도우미
│  ├─ features/          화면 (기능별 폴더)
│  │  ├─ editor/         트리 목록, 편집기, 그래프 배치, 내용 편집
│  │  ├─ flash/          플래시카드, 오늘의 복습, 미니맵
│  │  ├─ dnd/            빈칸 퀴즈, 백지 퀴즈
│  │  ├─ share/          공유 설정, 공유 보기, 갤러리, 동기화 상태 표시
│  │  ├─ account/        로그인, 계정, 병합 대화, 공지 배너, 개인정보 처리방침
│  │  ├─ admin/          관리자 화면

│  └─ ui/                작은 공용 부품 (아이콘, 시트, 툴팁, 아바타 등)

│  ├─ index.ts           서버 조립과 시작
```

코드 양은 `src/`가 TypeScript 약 8,200줄과 CSS 약 1,400줄, `server/`가 TypeScript 약 2,300줄이다 (점검 스크립트 포함). 가장 큰 파일은 `src/features/editor/EditorPage.tsx`(1,188줄)와 `src/core/sync/engine.ts`(560줄)다. **이 두 파일을 이해하면 앱의 절반을 이해한 것이다.**

### 의존 방향

```
features/  ──▶  core/  ──▶  (브라우저 API, Dexie, ts-fsrs)
    │
    └──────▶  ui/

server/  ──▶  src/core/types.ts 의 CAP (한도 상수 하나만 가져다 쓴다)
```

- `core/`는 화면을 모른다. 화면에 소식을 전하는 길은 알림(토스트)과 `dd:remote` 이벤트 둘뿐이다. `dd:remote`는 "서버에서 받은 변경을 적용했다"는 신호다 ([원리 3](#원리-3-화면은-자기-사본을-들고-있다-db가-바뀌어도-자동으로-다시-그려지지-않는다)).
- 서버와 클라이언트는 한도 상수 `CAP`만 공유한다. 서버가 `src/core/api.ts`를 참조하는 것은 타입뿐이다.
- **`features/` 안의 폴더끼리는 서로 가져다 쓴다.** 폴더 이름만 보고 "이 파일은 이 화면 전용"이라고 생각하면 안 된다. 아래 파일들은 사실상 공용이다.

| 파일 | 만든 곳 | 가져다 쓰는 곳 |
|---|---|---|
| `editor/graph/layout.ts` (카드 배치) | 편집기 | 플래시의 미니맵, 퀴즈의 캔버스 |
| `editor/content/format.ts` (내용 형식) | 편집기 | 플래시카드, 공유 보기 |
| `flash/study.ts` (학습 공용 도우미) | 플래시 | 빈칸, 백지 |
| `dnd/kit.tsx`, `dnd/dnd.ts` (범위 고르기, 섞기) | 퀴즈 | 플래시 |
| `share/ShareSheet.tsx`, `SyncStatus.tsx`, `VisibilityBadge.tsx` | 공유 | 트리 목록 |
| `flash/FlashPage`, `dnd/DndPage`, `dnd/BlankDndPage` (화면 전체) | 각 폴더 | 공유 보기 |

## 3. 먼저 알아야 할 다섯 가지 원리

코드 곳곳이 이 다섯 가지를 전제로 쓰여 있다. 먼저 알고 읽으면 "왜 이렇게 했지?"가 줄어든다.

### 원리 1. 노드가 곧 학습 항목이다

학습용 데이터가 따로 있지 않다. 트리의 **노드** 하나가 학습 항목 하나다. 학습 기록(`srs` 테이블)은 노드 id를 열쇠로 저장된다.

학습 모드는 같은 트리를 다르게 보여 줄 뿐이다.

- 플래시카드: 자식이 있는 노드가 "문제", 그 자식들이 "답"이다.
- 빈칸: 리프(자식이 없는 맨 끝 노드)를 뽑아서 제자리에 돌려놓게 한다.
- 백지: 루트를 뺀 모든 노드를 뽑아서 트리를 다시 만들게 한다.

그래서 노드 id가 유지되는지가 중요하다.

| 동작 | 노드 id | 학습 기록 |
|---|---|---|
| 잘라내기·붙여넣기, 들여쓰기, 순서 바꾸기 | 유지 | 따라간다 |
| 가지 복제, 공유 트리를 내 트리로 복제 | 새로 발급 | 따라가지 않는다 |

### 원리 2. 내 데이터의 진실은 브라우저에 있다 (로컬 우선)

내 트리, 노드, 학습 기록을 다루는 화면은 **서버에 묻지 않는다.** 항상 IndexedDB에서 읽고 IndexedDB에 쓴다. 서버 동기화는 그 뒤에서 따로 돈다.

- 로그인하지 않은 사용자는 편집과 학습을 서버 없이 한다. 앱이 켜질 때 로그인 여부를 확인하는 요청(`GET /api/me`)이 한 번 나가지만, 실패해도 그대로 동작한다. 그 뒤 편집과 학습으로는 요청이 나가지 않는다.
- 한 번도 로그인한 적 없는 기기는 outbox도 쓰지 않고, 동기화 엔진 코드도 내려받지 않는다.

서버에 직접 묻는 것은 다음뿐이다.

- 로그인 상태와 계정 정보 (`core/me.ts`)
- 남의 데이터: 공유 보기, 갤러리
- 관리자 화면
- **서버가 진실인 값**: 공개 범위, 공유 링크(slug), 관리자 숨김 여부. 이 셋은 서버에 요청한 뒤 응답을 로컬에 반영한다.

### 원리 3. 화면은 자기 사본을 들고 있다. DB가 바뀌어도 자동으로 다시 그려지지 않는다

편집기는 트리를 열 때 노드를 한 번 읽어 React 상태에 넣는다. 그 뒤로는 그 사본을 직접 고치고, 같은 내용을 IndexedDB에 따로 쓴다. "DB를 지켜보다가 바뀌면 화면을 다시 그리는" 구조가 **아니다.**

그래서 화면이 모르는 사이에 DB가 바뀌면 누군가 알려 줘야 한다. 그런 경우는 동기화가 서버 변경을 적용했을 때다. 이때 동기화 엔진이 `window`에 `dd:remote` 이벤트를 쏜다.

- 이 이벤트를 듣고 다시 읽는 화면: 편집기, 트리 목록, 계정 화면.
- 듣지 않는 화면: 플래시카드, 빈칸, 백지, 복습. 이 화면들은 열 때 읽은 내용으로 끝까지 간다.
- 같은 브라우저의 다른 탭에서 고친 것을 알려 주는 장치는 없다. 다른 탭의 변경은 새로 고치거나 화면을 다시 열어야 보인다.

### 원리 4. 충돌은 "나중에 쓴 쪽이 이긴다"로 푼다 (LWW)

두 기기가 같은 노드를 고치면 수정 시각(`updatedAt`)이 더 큰 쪽이 **그 노드 전체**를 차지한다. 이것을 LWW(Last-Write-Wins)라고 부른다. 버전 번호도, 필드별 병합도 없다.

> 예: 기기 A가 노드의 제목만 고치고, 기기 B가 같은 노드의 내용만 고쳤다. 나중에 고친 쪽의 노드가 통째로 남는다. 먼저 고친 쪽의 변경은 사라진다.

예외는 둘이다.

- 학습 기록의 "정답을 맞힌 날짜 목록"(`autoCorrectDays`)은 진 쪽 것도 버리지 않고 합친다.
- 공개 범위, slug, 관리자 숨김은 LWW와 무관하게 항상 서버 값이다.

삭제는 "지웠다는 표시"로 남겨서 전파한다. 이 표시를 **톰스톤**이라고 부른다. 톰스톤은 7일 뒤에 실제로 지워진다. 휴지통 복구 기한, 탈퇴 취소 기한도 같은 7일을 쓴다.

### 원리 5. 규칙은 화면 파일이 아니라 순수 로직 파일에 있다

배치 계산, 채점, 개요 변환, 간격 반복처럼 화면과 무관한 계산은 DOM과 DB를 건드리지 않는 파일로 분리돼 있다. 무언가의 **규칙**이 궁금하면 화면 파일(`*Page.tsx`)보다 이 파일들을 먼저 읽는 것이 빠르다.

| 궁금한 것 | 읽을 파일 |
|---|---|
| 카드가 어디에 놓이는가 | `features/editor/graph/layout.ts` |
| 내용의 서식 표기 | `features/editor/content/format.ts` |
| 플래시카드에 무엇이 나오는가 | `features/flash/flash.ts` |
| 퀴즈를 어떻게 채점하는가 | `features/dnd/dnd.ts` |
| 다음 복습일과 색 | `core/srs/index.ts` |
| 붙여 넣은 텍스트가 어떻게 트리가 되는가 | `core/outline.ts` |

각 파일 옆에는 `*.check.ts`라는 자가 점검 스크립트가 있다. 자세한 내용은 [12장](#12-테스트)에 있다.

## 4. 데이터 모델

핵심 타입은 `src/core/types.ts` 한 파일에 있다. 세 가지만 알면 된다.

### Tree: 트리 한 그루

| 필드 | 뜻 |
|---|---|
| `id` | UUID |
| `title` | 트리 제목. 루트 노드의 제목과 같은 값이다. 로컬에서 쓸 때마다 둘을 맞춘다 |
| `createdAt`, `updatedAt` | 시각 (밀리초). `updatedAt`이 충돌 판정 기준 |
| `visibility` | 공개 범위. `private`(기본) / `unlisted`(링크를 아는 사람만) / `public`(갤러리 노출) |
| `slug` | 공유 링크 토큰. 11자. 서버가 발급 |
| `sourceTreeId` | 남의 트리를 복제했다면 원본 id |
| `deletedAt` | 있으면 휴지통에 있는 트리 |

### TreeNode: 노드 하나

| 필드 | 뜻 |
|---|---|
| `id`, `treeId` | 자기 id와 소속 트리 |
| `parentId` | 부모 노드 id. **`null`이면 루트.** 트리마다 루트는 하나 |
| `order` | 형제 사이의 순서. 숫자. 두 노드 사이에 끼울 때는 두 값의 중간값을 쓴다 |
| `title` | 짧은 제목 (최대 200자) |
| `note` | 내용 (최대 5,000자). 형식은 [6.2의 "내용 형식"](#내용note-형식) 참고. 코드 주석 일부는 "메모"라고 부른다 |
| `aliases` | 별칭. 같은 뜻의 다른 표현 목록. 편집하고 공유 보기에 표시할 수 있지만 **지금은 어떤 채점도 별칭을 보지 않는다** |
| `collapsed` | 접혀 있는지 |
| `offset` | 편집기에서 카드를 손으로 끌어 옮긴 거리 `{x, y}` |
| `width` | 카드 너비 단계 1 / 2 / 3 |
| `updatedAt` | 충돌 판정 기준 |

트리 구조는 **부모 포인터 방식**이다. DB에는 노드가 평평한 목록으로 들어 있고, 읽은 뒤 메모리에서 `parentId`로 조립한다.

### NodeSrs: 노드 하나의 학습 기록

| 필드 | 뜻 | 지금 쓰이는가 |
|---|---|---|
| `nodeId` | 열쇠. 노드당 한 행 | 쓰임 |
| `card` | ts-fsrs 라이브러리의 상태 객체를 그대로 저장한 것. (이름이 `card`지만 화면의 카드와 무관하다) | 쓰임 |
| `due` | 다음 복습 시각. `card` 안의 값과 같고, 검색용으로 밖에 꺼내 둔 것 | 쓰임 |
| `miss` | 오답 점수. 틀리면 +1, 맞으면 -1, 0 아래로는 안 내려간다 | 쓰임 (편집기의 붉은 농도) |
| `lastGradeSource` | 마지막 채점의 종류 | 쓰임. 지금은 "맞음", "틀림" 두 값만 기록된다 |
| `autoCorrectDays` | 정답을 맞힌 날짜 목록 | 기록은 된다. 이 값을 읽는 "가지 완료" 판정 함수는 화면에서 쓰지 않는다 |
| `lastStructure`, `pendingRecheck` | 위치가 맞았는지, 재확인 대기 중인지 | 초기 설계의 흔적. 지금 화면에서는 의미 있게 쓰이지 않는다 |

### 저장 한도 CAP

`types.ts` 맨 아래의 `CAP`이 한도다. **서버도 이 상수를 가져다 쓴다.**

| 항목 | 한도 | 브라우저가 미리 막는가 |
|---|---|---|
| 제목 | 200자 | 막는다 |
| 트리당 노드 | 5,000개 | 막는다 |
| 사용자당 트리 | 200개 | 로그인했을 때만 막는다 |
| 내용 | 5,000자 | 편집기가 넘는 입력을 막고 토스트를 띄운다. 개요 가져오기도 잘라 넣는다. 그래도 넘은 행은 서버가 거부해 격리된다 ([7장의 "격리"](#문제가-생겼을-때의-처리)) |

### 저장소 두 곳의 테이블 대응

같은 데이터가 브라우저(IndexedDB, `src/core/db.ts`)와 서버(SQLite, `server/migrations/`)에 있다. 필드 이름은 브라우저가 camelCase, 서버가 snake_case이고, `server/sync/map.ts`가 둘 사이를 변환한다.

| 브라우저 테이블 | 서버 테이블 | 내용 | 동기화 |
|---|---|---|---|
| `trees` | `trees` | 트리 | 양방향 |
| `nodes` | `nodes` | 노드 | 양방향 |
| `srs` | `srs` | 학습 기록 | 양방향 |
| `attempts` | `attempts` | 백지 시도 집계 | 올리기만. 현재 기록하는 코드가 없다 |
| `events` | 없음 | 사용 이벤트 기록 | 안 함. 로컬에만 쌓인다 |
| `outbox` | 없음 | 서버로 올릴 변경 목록 | 동기화가 쓰는 장부 |
| `meta` | 없음 | 로그인했던 사용자 id, 어디까지 받았는지 | 동기화가 쓰는 장부 |
| 없음 | `users`, `sessions` | 계정, 로그인 세션 | 서버 전용 |
| 없음 | `user_seq` | 사용자별 변경 번호 ([7장](#7-동기화)) | 서버 전용 |
| 없음 | `audit_log`, `settings`, `reports` | 관리 기록, 공지·점검 설정, 신고 | 서버 전용 |
| 없음 | `ratings` | 공개 트리 별점. 사용자 한 명이 트리 하나에 한 표(1~5), 수정 가능. 트리를 실제 삭제하면 함께 지워진다 | 서버 전용 |

삭제 방식은 대상마다 다르다.

| 대상 | 브라우저에서 | 서버에서 |
|---|---|---|
| 트리 | `deletedAt`만 찍는다 (휴지통). 7일 뒤 실제 삭제 | 톰스톤으로 표시, 7일 뒤 실제 삭제 |
| 노드 | 바로 지운다. 학습 기록도 함께 지운다 | 톰스톤으로 표시, 7일 뒤 실제 삭제 |

## 5. 클라이언트: 앱이 켜지고 화면이 뜨기까지

### 부팅 순서

1. `index.html`의 인라인 스크립트가 저장된 테마를 먼저 적용한다. 화면이 번쩍이는 것을 막기 위해서다.
2. `src/main.tsx`가 `<App />`을 그린다.
3. `App.tsx`가 `core/me.ts`를 불러온다. 이 파일은 불러오는 순간 `GET /api/me`를 호출해 로그인 여부를 확인한다.
4. `App`이 `useRoute()`로 현재 주소를 해석하고, 해당 화면의 코드를 내려받아 그린다.
5. `/api/me`가 성공하면 그때 동기화 엔진 코드(`sync/engine.ts`)를 내려받아 시작한다. 실패(비로그인, 오프라인)하면 엔진 없이 그대로 동작한다.

첫 화면에 필요한 코드만 먼저 받고, 나머지 화면의 코드는 브라우저가 한가할 때 미리 받아 둔다. 관리자 화면 코드는 관리자일 때만 받는다. `core/sync.ts`와 `sync/engine.ts`가 나뉘어 있는 것도 이 때문이다. 작은 `sync.ts`만 첫 화면에 싣고, 큰 엔진은 필요할 때 받는다.

### 라우팅

`src/router.ts`는 라이브러리 없이 직접 만든 라우터다. 규칙은 두 가지다.

- 대부분의 화면은 주소의 `#` 뒷부분(해시)으로 구분한다.
- 공유 보기만 일반 경로(`/t/<slug>`)를 쓴다. 메신저에 링크를 붙였을 때 미리보기가 나오려면 서버가 그 주소를 보고 미리보기 정보를 넣어 줘야 하는데, 해시는 서버로 전달되지 않기 때문이다.

| 주소 | 라우트 이름 | 화면 컴포넌트 |
|---|---|---|
| `#/` | `trees` | `features/editor/TreeListPage` |
| `#/tree/<id>` | `edit` | `features/editor/EditorPage` |
| `#/tree/<id>/flash` | `flash` | `features/flash/FlashPage` |
| `#/tree/<id>/dnd` | `dnd` | `features/dnd/DndPage` (화면 이름은 "빈칸") |
| `#/tree/<id>/blank` | `blank` | `features/dnd/BlankDndPage` (화면 이름은 "백지") |
| `#/review` | `review` | `features/flash/ReviewPage` |
| `#/login` | `login` | `features/account/LoginPage` |
| `#/account` | `account` | `features/account/AccountPage` |
| `#/admin`, `#/admin/users`, `/trees`, `/system` | `admin` | `features/admin/AdminPage` |
| `#/gallery` | `gallery` | `features/share/GalleryPage` |
| `#/privacy` | `privacy` | `features/account/PrivacyPage` |
| `/t/<slug>`, `/t/<slug>?m=flash` (`dnd`, `blank`도 가능) | `shared` | `features/share/SharedPage` |

> **이름 주의.** 코드의 `dnd`는 화면의 "빈칸", 코드의 `blank`는 화면의 "백지"다. 둘 다 `features/dnd/` 폴더에 있다. 코드를 찾을 때 자주 헷갈린다.

**`?root=`: 가지 하나만 다루기.** 트리 화면 네 개(편집·플래시·빈칸·백지)는 주소 끝에 `?root=<노드 id>`를 붙일 수 있다. 예: `#/tree/abc/flash?root=n42`. 그 노드 아래의 가지만 다룬다는 뜻이다. 같은 장치를 화면마다 다르게 부른다. 편집기에서는 "이 가지만 보기"(코드에서는 포커스), 학습 모드에서는 "범위"(코드에서는 `scope`)다.

### App.tsx가 그리는 틀

```
<nav.topnav>     브랜드 · 내 트리 · 오늘의 복습(남은 개수) · 테마 · 계정
<Banners />      점검 중 안내, 공지 한 줄
<main>           현재 주소에 맞는 화면 하나
<Toaster />      토스트: 화면 아래에 잠깐 뜨는 알림 (한 번에 하나)
<TooltipLayer /> 툴팁
```

로그인이 필요한 화면을 막는 공통 관문은 없다. 각 화면이 알아서 처리한다. 예를 들어 관리자 화면은 관리자가 아니면 `#/`로 보낸다.

### 앱 전체가 공유하는 상태

로그인 정보, 동기화 상태, 토스트 대기열처럼 여러 화면이 같이 보는 값은 상태 관리 라이브러리 없이 만들었다. 값은 각 파일 맨 위의 변수에 두고, 화면은 훅으로 읽는다.

| 값 | 두는 곳 | 화면이 읽는 방법 |
|---|---|---|
| 로그인한 사용자 | `core/me.ts` | `useMe()` |
| 동기화 상태 | `core/sync.ts` | `useSyncState()` |
| 토스트 대기열 | `features/Toast.tsx` | `toast()`로 넣고 `<Toaster />`가 그린다 |

### 서버 호출

`src/core/api.ts`의 `api()` 함수 하나가 모든 서버 호출을 맡는다. 주소는 항상 `/api/...`로 시작하는 상대 경로다. 실패하면 `ApiError`를 던진다. `status`가 `0`이면 오프라인이라는 뜻이다.

## 6. 화면별 동작

### 6.1 트리 목록 (`TreeListPage.tsx`)

- 열릴 때 7일이 지난 휴지통 트리를 정리하고 목록을 읽는다.
- 트리 만들기는 `repo.createTree()`다. 트리 한 행과 루트 노드 한 행을 같이 만든다.
- 삭제는 확인 창 없이 바로 휴지통으로 보내고 [되돌리기] 토스트를 띄운다. 휴지통은 계정 화면에 있다.
- 목록의 트리 항목을 누르면 `#/tree/<id>`로 이동한다.

### 6.2 편집기 (`EditorPage.tsx`)

앱에서 가장 큰 화면이다. 구조를 먼저 잡고 읽어야 한다.

#### 화면은 그래프 하나다

편집기에는 목록 보기가 없다. **카드 그래프 하나**만 있고, 방향만 두 가지다. 화면의 이름은 형제가 놓이는 방향을, 코드 값은 트리가 자라는 방향을 가리켜서 서로 반대로 읽힌다.

| 화면 이름 | 코드 값 | 모양 |
|---|---|---|
| 가로 보기 (기본) | `dir = 'down'` | 트리가 아래로 자란다. 형제가 옆으로 나란히 놓인다 |
| 세로 보기 | `dir = 'right'` | 트리가 오른쪽으로 자란다. 형제가 위아래로 쌓인다 |

파일 이름과 클래스 이름에 "outline", "NodeRow" 같은 말이 남아 있지만 예전 이름의 흔적이다. `NodeRow`는 그래프 안의 카드 한 장이다.

#### 컴포넌트 구성

```
EditorPage                     상태, 저장, 키보드, 확대·축소 전부 담당
├─ TreeHeader                  트리 제목 + 모드 탭 (편집·플래시·빈칸·백지)
├─ GraphView                   카드 크기를 재고, 배치하고, 선을 그린다
│  └─ NodeRow × 보이는 노드 수   카드 한 장 (제목, 내용, 접기 배지, 너비 손잡이)
│     └─ NoteEditor             카드 안에서 내용을 고칠 때
├─ SearchBox                   제목 검색
└─ 오른쪽 패널
   ├─ DetailPanel               선택한 노드의 제목·별칭·내용·너비 편집
   │  └─ NoteEditor
   └─ 개요 붙여넣기 · 내보내기 칸
```

`DetailPanel`, `Aliases`, `SearchBox`는 별도 파일이 아니라 `EditorPage.tsx` 아래쪽에 들어 있다.

#### 편집 한 번이 저장되기까지

노드를 추가하든 제목을 고치든 모든 변경은 같은 길을 지난다.

1. 핸들러가 **새 노드 배열**을 만든다. 바뀐 노드만 새 객체로 바꾸고 나머지는 같은 객체를 그대로 둔다.
2. `commit(새 배열, 이름)`을 부른다. 이름은 되돌리기 알림에 쓰는 글자다 (예: `'제목 편집'`).
3. `commit`이 저장을 **시작만 하고 기다리지 않는다.** `persist(이전 배열, 새 배열)`을 부르면:
   - `persist`가 두 배열을 비교해 **객체가 달라진 노드**(같은 객체인지를 `!==`로 비교)만 고른다.
   - 고른 노드를 `repo.putNodes()`에, 사라진 노드를 `repo.deleteNodes()`에 넘긴다.
   - `putNodes`는 트랜잭션 하나 안에서 노드를 쓰고, 트리의 `updatedAt`을 올리고, outbox에 "이 노드가 바뀌었다"를 적는다. (outbox 기록은 이 기기가 로그인한 적이 있을 때만 된다.)
4. `commit`이 이전 배열을 되돌리기 목록에 넣는다.
5. `commit`이 `setNodes(새 배열)`로 화면을 갱신한다.

즉 화면이 먼저 바뀌고 DB 쓰기는 뒤에서 끝난다. 쓰기에 실패하면 토스트로 알린다.

이 구조에서 지켜야 할 규칙이 하나 나온다.

> **노드 객체의 필드를 직접 바꾸면 안 된다.** 저장할 대상을 찾는 것도, 카드 크기를 다시 잴지 정하는 것도 "객체가 바뀌었는가"로 판단한다. `node.title = '...'`처럼 기존 객체를 고치면 같은 객체라서 저장도 재측정도 빠진다. 항상 `{ ...node, title: '...' }`처럼 새 객체를 만든다.

#### 되돌리기

- 되돌리기 한 단계는 **노드 배열 전체의 스냅샷**이다. 최대 50단계.
- 접기·펼치기는 되돌리기 대상이 아니다. 오른쪽 패널에서 글자를 입력할 때는 입력칸에 들어간 순간부터 나올 때까지가 한 단계로 묶인다.
- 노드를 삭제하면 [실행 취소] 토스트가 10초 동안 뜬다. 그 사이 다른 편집을 했다면 토스트의 실행 취소는 동작하지 않는다.

#### 편집 중에 다른 기기의 변경이 들어오면

편집기는 `dd:remote` 이벤트를 받으면 그 트리의 노드를 DB에서 다시 읽어 화면의 배열을 통째로 바꾼다. 이때 두 가지를 지킨다.

- 지금 입력 중인 노드는 화면의 값을 그대로 둔다. 치던 글자가 덮이지 않는다.
- 되돌리기·다시 실행 목록은 비운다. 옛 상태를 되살리면 다른 기기가 방금 만든 노드를 지우게 되기 때문이다.
- 학습 기록(카드 색)도 다시 읽는다.

#### 무엇이 보이는가: 접기, 보기 깊이, 이 가지만 보기

카드가 화면에 나올지는 네 가지가 함께 정한다.

| 장치 | 저장되는 곳 | 설명 |
|---|---|---|
| 접기 (`collapsed`) | 노드. 동기화된다 | 사용자가 접은 노드 |
| 보기 깊이 (`viewDepth`) | 이 기기 | 1·2·3단계 또는 전체. 그 아래는 숨긴다 |
| 임시 펼침 (`reveal`) | 저장 안 됨 | 보기 깊이를 넘어 잠깐 펼친 노드 |
| 이 가지만 보기 (`?root=`) | 주소 | 그 노드를 꼭대기로 삼아 아래만 본다 |

선택한 노드, 배율, 스크롤 위치, 보기 깊이는 트리마다 `localStorage`의 `dd:editor-view:<treeId>`에 저장된다. 방향은 `dd:editor-dir`에 저장되고 모든 트리에 공통이다.

노드가 1,000개를 넘는 트리를 처음 열면 보기 깊이를 3으로 시작한다. 그 밖의 대형 트리용 장치는 없다. 보이는 카드는 전부 화면 요소(DOM)로 만들어진다.

#### 카드가 자리를 잡는 과정

`graph/layout.ts`의 `layout()`은 화면을 모르는 순수 함수다. 노드 목록과 "카드 크기를 알려 주는 함수"를 받아서 카드마다 좌표를 돌려준다. (가로 보기 기준으로 설명한다.)

1. 아래에서 위로 올라가며 각 가지의 폭을 구한다. 가지의 폭은 자식 가지들의 폭을 합친 것과 자기 카드 폭 중 큰 값이다. 부모는 첫 자식과 마지막 자식의 가운데에 놓인다.
2. 같은 깊이의 카드는 같은 줄에 놓는다. 줄의 높이는 그 깊이에서 가장 큰 카드에 맞춘다.
3. 위에서 아래로 내려가며 실제 좌표를 정한다. 이때 손으로 옮긴 거리(`offset`)를 더하고, 그 값은 자손에게도 누적된다. 부모 카드를 끌면 자손이 따라 움직이는 이유다.

카드 크기는 내용에 따라 달라서 그려 보기 전에는 모른다. 그래서 `GraphView`가 두 번에 걸쳐 그린다. 먼저 임시 크기로 배치해 화면 요소를 만들고, 실제 크기를 잰 뒤 다시 배치한다. 매번 모든 카드를 재지는 않고, 새로 생긴 카드와 노드 객체가 바뀐 카드만 다시 잰다.

보이는 카드의 크기가 모두 확정될 때마다 `GraphView`가 `onSettled`를 부른다. 처음 열 때뿐 아니라 카드가 추가·삭제되거나 접을 때도 불린다. `EditorPage`는 이때 예약해 둔 일이 있으면 한다. 저장해 둔 스크롤 위치 복원, 화면에 넘칠 때의 자동 축소, 특정 카드를 가운데로 옮기기가 그런 일이다.

#### 확대·축소와 이동

- 확대·축소는 CSS `transform: scale()`이다. 배치 계산은 배율과 무관하게 한 번만 한다.
- 화면 이동은 스크롤이다. 빈 곳을 끌면 스크롤 값이 바뀐다.
- 카드를 끄는 것은 **구조를 바꾸지 않는다.** 위치(`offset`)만 바꾼다. 다른 카드 근처에 놓아도 부모가 바뀌지 않는다. 구조를 바꾸려면 키보드, 잘라내기·붙여넣기, 터치용 구조 바(화면 위쪽의 구조 편집 버튼 줄)를 쓴다.

#### 키보드: 두 가지 모드

**탐색 모드** — 그래프 영역에 포커스가 있을 때. 처리 함수는 `onNavKey`.

| 키 | 동작 |
|---|---|
| 방향키 | 부모, 첫 자식, 같은 깊이의 이웃으로 이동 |
| Enter | 아래에 형제 추가 |
| Space, F2 | 제목 편집 시작 |
| H | 접기·펼치기 |
| Delete | 삭제 |
| Ctrl+Z / Ctrl+Shift+Z, Ctrl+Y | 되돌리기 / 다시 실행 |
| Ctrl+X, Ctrl+V | 잘라내기, 붙여넣기 (가지 옮기기) |
| Alt+←, Alt+→ | 형제 사이에서 순서 바꾸기 |
| `=`, `-`, `0` | 확대, 축소, 100% |

**편집 모드** — 카드 제목을 입력하는 중. 처리 함수는 `onEditKey`.

| 키 | 동작 |
|---|---|
| Enter | 저장하고 아래에 형제를 만들어 이어서 입력 |
| Tab, Shift+Tab | 들여쓰기, 내어쓰기 |
| Esc | 저장하고 끝 |

알아 둘 것:

- `/`(검색)는 `onNavKey`가 아니라 `window`의 키 리스너가 따로 처리한다.
- 글자 키 대부분은 `e.code`(키보드의 물리적 위치)로 판정한다. 한글 입력 상태에서도 단축키가 동작하게 하려는 것이다. `.`, `?`, `/`는 `e.key`로 판정한다.
- 한글 조합 중(`isComposing`)에는 모든 키 처리를 건너뛴다.
- 단축키 전체 목록은 `EditorPage.tsx`의 `KEYS` 배열에 있다. 화면의 단축키 표가 이 배열로 그려진다.

#### 내용(note) 형식

내용은 HTML도 마크다운도 아닌 **자체 형식의 일반 텍스트**다. 규칙은 `content/format.ts`에 있다.

| 표기 | 뜻 |
|---|---|
| 줄 맨 앞 `- ` | 불릿 |
| `==y:글자==` | 노란 형광펜 |
| `==p:글자==` | 분홍 형광펜 |
| `==b:글자==` | 하늘색 형광펜 |

지원하는 서식은 이것이 전부다. 굵게, 링크, 제목은 없다.

`NoteEditor.tsx`는 브라우저의 편집 가능 영역(`contentEditable`)을 React를 거치지 않고 직접 다룬다. 입력할 때마다 화면 요소를 읽어 위 형식으로 바꾸고, 다시 HTML로 만들어 비교한 뒤 다르면 고쳐 그린다. 붙여넣기는 일반 텍스트만 받고, 화면에 그릴 때는 `<`, `>`, `&`를 안전한 표기로 바꾼다. 그래서 임의의 HTML이 저장되거나 실행될 길이 없다.

#### 개요 붙여넣기와 내보내기

오른쪽 패널 아래의 "개요 붙여넣기 · 내보내기" 칸에서 한다.

- **붙여넣기**: 들여쓰기된 텍스트를 붙여 넣으면 트리가 된다. 변환 규칙은 `core/outline.ts`에 있다.
  - 줄 앞의 불릿 기호와 번호는 떼어 낸다.
  - `# 제목` 같은 마크다운 제목 줄 아래의 줄은 그 제목의 자식이 된다.
  - `제목 :: 내용` 형식으로 한 줄짜리 내용을 같이 넣을 수 있다.
  - 200자를 넘는 제목은 잘라서 넘친 부분을 내용으로 옮긴다.
- **내보내기**: [개요 내보내기] 버튼이 트리를 같은 형식의 텍스트로 만든다. 패널의 "이 가지 내보내기" 버튼은 선택한 가지만 복사한다. 여러 줄짜리 내용은 내보내지지 않는다.

### 6.3 학습 모드의 공통 구조

학습 화면 세 개는 DB를 직접 읽지 않는다. `core/source.ts`에 정의된 **`StudySource`** 라는 창구를 통한다. 창구의 구현은 둘이다.

| 구현 | 정의된 곳 | 어디서 쓰나 | 기록이 남는가 |
|---|---|---|---|
| `dexieSource(treeId)` | `core/source.ts` | 내 트리 학습 | IndexedDB에 저장되고 동기화된다 |
| `memorySource(...)` | `features/share/SharedPage.tsx` | 공유 보기의 체험 학습 | 메모리에만. 탭을 닫으면 사라진다 |

이 덕분에 같은 `FlashPage`, `DndPage`, `BlankDndPage`가 내 트리와 남의 공유 트리 양쪽에서 그대로 쓰인다.

**채점은 "맞음/틀림" 두 가지만 기록한다.** 세 모드 모두 같은 길로 저장한다.

1. 화면이 `source.record(노드 id, 맞았는가)`를 부른다.
2. `srs/index.ts`의 `recordResult`가 맞음은 Good, 틀림은 Again으로 바꾼다. (ts-fsrs가 쓰는 등급 이름이다.)
3. ts-fsrs가 다음 복습 시각을 계산한다. 맞으면 간격이 늘고, 틀리면 몇 분 뒤로 잡힌다.
4. `srs` 테이블에 쓰고 outbox에 기록한다.

간격 계산에는 약간의 무작위를 넣는다. 같은 날 푼 항목의 복습일이 한날에 몰리지 않게 하려는 것이다.

### 6.4 플래시카드 (`FlashPage.tsx`, `FlashCard.tsx`, `flash.ts`)

- **문제**는 자식이 있는 노드다. 코드에서는 이것을 "개념"이라고 부른다 (`conceptsIn`). 리프는 문제가 되지 않는다.
- **답**은 그 노드의 직계 자식들이다. 누르기 전에는 가려져 있다.
- 자식마다 [알음]/[모름]을 누른다. **학습 기록이 바뀌는 것은 문제로 나온 노드가 아니라 그 자식 노드다.**
- 마지막 문제까지 가면, 모름이 있던 개념을 한 번 더 뒤에 붙여서 다시 묻는다.
- 진행 상황은 `localStorage`의 `flash:<treeId>:<범위>`에 저장한다. 7일이 지나거나 트리 구성이 바뀌면 버린다.
- 옆의 미니맵(`Minimap.tsx`)은 트리 전체의 축소판이다. 편집기의 `layout()`을 글자 없는 작은 상자로 다시 그린 것이다. 노드가 100개를 넘으면 숨긴다.

### 6.5 오늘의 복습 (`ReviewPage.tsx`)

- `srs` 테이블에서 `due`가 **오늘 23:59:59 이전**인 행을 찾아 트리별로 묶는다. "지금" 기준이 아닌 이유는, 방금 틀린 항목의 다음 기한이 몇 분 뒤라서 지금 기준이면 목록에 안 보이기 때문이다.
- 기한이 된 노드의 **부모**를 문제로 삼아 플래시카드와 같은 화면을 쓴다. 기한이 된 자식에만 채점 버튼이 있고, 나머지 형제는 참고용으로 회색으로 보인다.
- 상단 바의 복습 개수는 `App.tsx`의 `countDue()`가 같은 기준으로 센다.

### 6.6 빈칸 퀴즈 (`DndPage.tsx`, 라우트 이름 `dnd`)

- 리프 자리를 빈칸으로 만든 뼈대 트리와, 뽑아낸 카드가 섞여 있는 트레이(카드 보관함)를 보여 준다.
- 카드를 끌어다 놓거나, 카드를 누른 뒤 빈칸을 누른다.
- 채점은 "같은 부모 아래에 있는가"만 본다. 형제 사이의 순서는 따지지 않는다. 제목이 같은 카드끼리는 서로 바꿔 놓아도 정답이다.
- 주소에 `?root=`가 없고 리프가 30개를 넘으면, 먼저 어느 가지부터 할지 고르게 한다.

### 6.7 백지 퀴즈 (`BlankDndPage.tsx`, 라우트 이름 `blank`)

- 루트만 놓인 화면과, 나머지 모든 노드가 섞인 트레이를 보여 준다.
- 카드를 루트나 이미 놓은 카드 위에 붙여서 트리를 만든다.
- 채점은 "루트부터 그 노드까지의 제목이 원본과 같은 순서로 이어지는가"를 본다. 부모 제목만 같아서는 안 된다. 서로 다른 가지에 같은 제목의 부모가 있을 수 있기 때문이다.
- 주소에 `?root=`가 없고 루트를 뺀 노드가 40개를 넘으면 가지를 먼저 고르게 한다.

두 퀴즈에 공통인 것:

- 채점 규칙은 `dnd.ts`의 `gradeDnd`, `gradeBlank`에 있다.
- 카드를 하나라도 놓고 채점하면 범위 안의 모든 대상 노드가 기록된다. 놓지 않은 카드는 틀림이다. **하나도 놓지 않고 채점하면 아무것도 기록하지 않는다.**
- 끌어 놓기는 `useDragDrop.ts`가 포인터 이벤트로 직접 구현했다. 마우스와 터치가 같은 코드로 처리된다.

### 6.8 색이 뜻하는 것

색 규칙은 `srs/index.ts`에 모여 있고, 화면마다 쓰는 색이 다르다.

**편집기 카드**는 붉은 농도 하나만 쓴다. 오답 점수(`miss`)가 높을수록 진하고, 4 이상이면 가장 진하다.

**플래시카드와 미니맵**은 숙련도를 네 단계로 보여 준다. "기억 확률"은 ts-fsrs가 "지금 이 항목을 기억하고 있을 확률"로 추정한 값이다.

| 상태 | 색 | 기호 |
|---|---|---|
| 마지막에 틀렸다 | 빨강 | ✕ |
| 맞혔고 기억 확률 90% 이상 | 초록 | ✓✓ |
| 기억 확률 80% 이상 | 연두 | ✓ |
| 그 밖 (오래됐거나 한 번도 풀지 않음) | 없음 | 없음 |

자식 중에 초록이 아닌 것이 있으면 부모는 초록이어도 연두로 낮춰 보여 준다.

### 6.9 공유 (`features/share/`)

- **공개 범위 바꾸기** (`ShareSheet.tsx`): 비공개 / 링크 / 공개 세 단계다. **로그인해야 바꿀 수 있다.** 공개하려면 노드가 3개 이상이고 제목이 있어야 한다. 바꾸기 직전에, 아직 안 올린 변경을 먼저 서버로 올린다(`flush`). 서버가 최신 내용을 갖고 있어야 하기 때문이다.
- **공유 보기** (`SharedPage.tsx`): `/t/<slug>`로 열리는 읽기 전용 화면이다. 탭이 네 개(보기·플래시·빈칸·백지)이고, 학습 탭은 체험용이라 기록이 남지 않는다.
- **복제**: 공유 트리를 새 id로 내 IndexedDB에 복사한다. 복사는 브라우저가 하고, 서버에는 복제 횟수만 올려 달라고 알린다.
- **갤러리** (`GalleryPage.tsx`): 공개 트리를 20개씩 보여 준다. 최신순과 복제 수 순, 제목 검색이 있다.
- **신고**: 공유 보기에서 사유를 골라 보낸다. 관리자 화면에 쌓인다.

### 6.10 계정과 관리자

- **로그인** (`LoginPage.tsx`): Google과 카카오 OAuth만 있다. 비밀번호 로그인은 없다. 새 창을 띄우지 않고 같은 창에서 이동한다. 카카오톡 같은 앱 안의 브라우저에서는 Google 버튼을 끄고 외부 브라우저로 여는 방법을 안내한다.
- **병합 대화** (`MergeDialog.tsx`): 로그인했는데 이 기기에 이미 트리가 있을 때 뜬다. 자세한 분기는 [7장의 시나리오 1](#시나리오-1-로그인-없이-쓰다가-처음-로그인한다)에 있다.
- **계정 화면** (`AccountPage.tsx`): 닉네임, 로그인된 기기 목록, 휴지통, 데이터 내보내기(`drilldown-export.json`), 백업 가져오기, 로그아웃, 탈퇴. 비로그인 상태에서도 휴지통과 내보내기·가져오기는 쓸 수 있다.
- **관리자 화면** (`AdminPage.tsx`): 탭이 네 개다. 대시보드, 사용자(정지·삭제), 공개 트리(숨김·신고 처리·복구), 시스템(공지, 점검 모드, 감사 로그).

## 7. 동기화

코드는 `src/core/sync/engine.ts`(브라우저)와 `server/sync/`(서버)에 있다.

### 한 문장 요약

브라우저는 **"무엇이 바뀌었는지"만 outbox에 적어 두고**, 2초 뒤에 그 항목들의 현재 값을 읽어 서버에 올린다. 서버는 변경마다 번호를 붙여 저장하고, 다른 기기는 "몇 번 이후로 바뀐 것을 달라"고 받아 간다.

### 미리 알 것 두 가지

**outbox는 "이 기기가 로그인한 적이 있을 때만" 쓴다.** outbox에 적는 함수는 `core/db.ts`의 `track()`이다. `track()`은 `meta` 테이블에 사용자 id가 있는지만 본다.

| 기기 상태 | `meta`의 사용자 id | outbox | 엔진 |
|---|---|---|---|
| 한 번도 로그인한 적 없음 | 없음 | 쓰지 않는다 | 없다 |
| 로그인 중 | 있음 | 쓴다 | 돈다 |
| 로그인했다가 로그아웃함 | **남아 있음** | 계속 쌓인다 | 멈춰 있다 |

로그아웃한 뒤의 편집도 outbox에 쌓이고, 같은 계정으로 다시 로그인하면 이어서 올라간다.

**번호가 두 종류다.**

| 이름 | 누가 매기나 | 뜻 |
|---|---|---|
| 서버의 `seq` | 서버 (`user_seq` 테이블) | 그 사용자의 변경에 붙는 일련번호. 변경이 저장될 때마다 1씩 오른다 |
| 커서 (`cursor`) | 브라우저 (`meta` 테이블) | 이 기기가 마지막으로 받은 서버 `seq`. 다음 pull의 시작점 |

브라우저 outbox에도 `seq`라는 필드가 있지만 로컬 행 번호일 뿐이고 서버의 `seq`와 무관하다.

### 노드 제목을 고쳤을 때 다른 기기에 닿기까지

**기기 A (고친 쪽)**

1. `repo.putNodes()`가 노드를 쓰면서 같은 트랜잭션에서 `track()`을 부른다.
2. `track()`이 outbox에 `{kind: 'node', id, op: 'put', at: 지금}` 한 행을 적는다. **내용은 적지 않는다.** 같은 노드를 또 고치면 새 행을 만들지 않고 그 행의 시각만 바꾼다. 삭제는 `op: 'del'`로 적는다.
3. 2초 동안 추가 변경이 없으면 엔진이 push를 시작한다.
4. outbox의 행마다 현재 값을 DB에서 읽어 `POST /api/sync`로 보낸다. 한 번에 최대 500행, 약 900KB까지다.

**서버**

5. `server/sync/push.ts`의 `applyPush`가 행마다 비교한다. 보낸 쪽의 `updatedAt`이 서버 것보다 **클 때만** 저장한다. 같으면 서버 것을 유지한다.
6. 저장하는 행마다 서버 `seq`를 1 올려 붙인다.
7. 응답으로 결과를 분류해 돌려준다.

| 응답 항목 | 뜻 | 브라우저의 처리 |
|---|---|---|
| `applied` | 반영됨 | outbox에서 지운다 |
| `superseded` | 서버 것이 더 새것이라 졌다 | 서버 값으로 덮는다. [시나리오 2](#시나리오-2-두-기기가-같은-노드를-다르게-고쳤다) 참고 |
| `dropped` | 대상이 없어서 버림 (예: 지워진 노드의 학습 기록) | outbox에서 지운다 |
| `id_taken` | 다른 사용자가 이미 쓰는 id | 새 id를 발급해 다시 보낸다. 학습 기록도 새 id로 옮긴다 |

**기기 B (받는 쪽)**

8. 60초마다, 또는 탭으로 돌아오거나 온라인이 될 때 `GET /api/sync?since=<커서>`를 부른다.
9. 서버(`pull.ts`)가 그 번호 이후에 바뀐 트리·노드·학습 기록을 최대 500행 돌려준다. 더 있으면 `more: true`를 붙이고, 브라우저는 이어서 다시 부른다.
10. 엔진의 `applyRemote`가 받은 행을 IndexedDB에 쓴다. 단, 그 항목에 아직 안 올린 내 변경이 있고 내 것이 더 새것이면 내 것을 둔다. 다음 push에서 내 것이 이긴다.
11. `window`에 `dd:remote` 이벤트를 쏜다. 열려 있는 편집기와 목록이 다시 읽는다.

### 언제 동기화가 도는가

| 계기 | 하는 일 |
|---|---|
| 로그인 직후 | push 후 pull |
| 데이터를 쓴 뒤 2초 | push만 |
| 온라인으로 돌아옴 | push 후 pull |
| 탭이 다시 보임 | push 후 pull |
| 60초마다 (보이는 탭만) | push 후 pull |
| 공개 범위를 바꾸기 직전 | 기다리지 않고 즉시 push (`flush`) |

동기화는 줄을 세워 한 번에 하나만 돈다. pull을 한 뒤에는 push를 한 번 더 한다. pull이 올릴 것을 새로 만들 수 있기 때문이다 (예: 부모를 잃은 노드를 루트 아래로 옮긴 결과).

### 시나리오 1. 로그인 없이 쓰다가 처음 로그인한다

1. 로그인 전: 편집이 IndexedDB에만 저장된다. outbox는 비어 있다.
2. 로그인 직후: `engine.onLogin()`이 이 기기의 트리 수와 계정의 트리 수를 센다.
3. 상황에 따라 묻거나 바로 진행한다.

| 상황 | 화면에 뜨는 것 | 동작 |
|---|---|---|
| 같은 계정으로 다시 로그인 | 없음 | 바로 동기화 시작 |
| 이 기기에 트리 없음 | 계정에 트리가 있으면 "계정의 트리 N개를 가져왔어요" 토스트 | 서버 것을 받는다 |
| 이 기기에 트리 있음 | 병합 대화: [저장] | 누르면 **이 기기의 모든 트리·노드·학습 기록을 outbox에 한꺼번에 넣고** 올린다. 그다음 서버 것을 받는다 |
| 전에 다른 계정으로 로그인했던 기기 | 병합 대화: [이 계정으로 복제] 또는 [이전 계정 트리 지우고 시작] | 복제는 기존 트리에 새 id를 줘서 이 계정에 넣는다. 학습 기록은 따라가지 않는다 |

병합 대화에서 아무것도 고르지 않고 닫을 수 있다(Esc, 바깥 누르기). 그러면 동기화가 시작되지 않고, 새로 고칠 때까지 그 상태로 남는다.

### 시나리오 2. 두 기기가 같은 노드를 다르게 고쳤다

`updatedAt`이 큰 쪽(나중에 고친 쪽)이 남는다. 진 쪽 사용자가 보는 것은 "언제 졌는지"에 따라 다르다.

| 경우 | 진 쪽 화면에서 일어나는 일 |
|---|---|
| 내 것을 올리다가 졌다 (서버에 이미 더 새것이 있었다) | 내 노드가 서버 값으로 바뀐다. "다른 기기 변경 반영됨 N건" 토스트가 8초 뜨고 [내 버전 유지] 버튼이 있다. 누르면 내 값의 시각을 지금으로 올려 다시 보낸다. 그러면 내 것이 이긴다 |
| 내 것을 먼저 올렸고, 나중에 다른 기기의 더 새것을 받았다 | 내 노드가 조용히 바뀐다. 토스트는 없다 |

편집기가 열려 있었다면 두 경우 모두 화면이 다시 읽힌다. 입력 중이던 노드는 덮이지 않는다 ([6.2](#편집-중에-다른-기기의-변경이-들어오면)).

기기 시계가 미래로 틀어져 있으면 그 기기가 계속 이기게 된다. 이를 줄이려고 서버가 5분 넘게 앞선 시각을 현재 시각으로 깎는다.

### 시나리오 3. 트리를 지웠다

지운 기기를 A, 다른 기기를 B라고 하자.

| 시점 | 일어나는 일 |
|---|---|
| A에서 삭제 | A의 트리에 `deletedAt`이 찍혀 휴지통으로 간다. outbox에 `op: 'del'` 행이 생기고 push로 서버에 전달된다. 서버는 그 트리를 톰스톤으로 표시한다 |
| 7일 안에 B가 켜짐 | B가 pull로 톰스톤을 받는다. B에서도 그 트리가 휴지통에 보인다 |
| 7일 안에 복구 | 계정 화면의 휴지통에서 복구한다. 서버에 `POST /api/trees/<id>/restore`를 먼저 부르고 로컬을 되살린다 |
| 7일이 지남 | 각 브라우저는 트리 목록을 열 때 휴지통에서 실제로 지운다. 서버는 매일 04시 정리 작업이 톰스톤을 실제로 지운다 |
| 서버가 정리한 뒤에야 B가 처음 켜짐 (예: 한 달 꺼져 있었음) | B의 커서가 너무 오래돼 서버가 410으로 답한다. B는 전체를 처음부터 다시 받는다. 그런데 B에는 그 트리가 멀쩡히 남아 있고 서버에는 흔적이 없으므로, B는 그것을 "이 기기에만 있는 트리"로 보고 **서버에 다시 올린다.** 지운 트리가 되살아난다. "이 기기에만 있던 트리 N개를 계정에 올렸습니다" 토스트가 뜬다 |

마지막 줄은 코드를 읽은 결론이고 실행으로 확인하지는 않았다. 데이터를 잃는 것보다 되살아나는 쪽을 택한 설계다.

노드 삭제도 같은 방식으로 전파된다. 다만 노드는 휴지통이 없다. 브라우저에서 바로 지워지고, 서버가 톰스톤을 7일 보관하며 다른 기기에 전달한다.

삭제된 트리에 딸린 노드와 학습 기록은 pull에서 내려보내지 않는다. 트리의 톰스톤 한 행이 전체를 대표한다. 복구하면 서버가 딸린 행에 새 `seq`를 붙여 다시 내려보낸다.

### 화면의 동기화 상태

트리 목록 화면 머리의 아이콘(`SyncStatus.tsx`)이 네 가지 상태를 보여 준다. 비로그인이면 아이콘이 없다.

| 상태 | 뜻 | 화면 |
|---|---|---|
| `saved` | 다 올렸고 다 받았다 | ✓ |
| `syncing` | 올리거나 받는 중 | 도는 아이콘 |
| `offline` | 연결이 없거나 서버가 점검 중 | "N건 대기". 누르면 다시 시도 |
| `error` | 실패 | 누르면 이유를 토스트로 보여 준다 |

### 문제가 생겼을 때의 처리

| 상황 | 엔진의 처리 | 사용자에게 보이는 것 |
|---|---|---|
| 오프라인 | outbox에 쌓아 두고 온라인이 되면 보낸다 | `offline` "N건 대기" |
| 서버가 요청 수 제한을 걺 (429) | 오류로 보지 않는다. 안내된 시간(없으면 15초)만큼 기다렸다가 다시 시도 | `syncing` 유지 |
| 서버 점검 중 (503) | 안내된 시간(없으면 30초) 뒤 다시 시도 | `offline`, 점검 배너 |
| 로그인이 풀림 (401) | 멈추고 로그인 상태를 다시 확인 | `error` "다시 로그인해 주세요" |
| 트리 200개 한도 초과 | 넘친 트리를 찾아 **보류**한다(코드의 `held`). 올리지 않고 두었다가, 트리를 지워 자리가 나면 올린다 | `error` "트리는 200개까지 저장할 수 있습니다 — N개 보류" |
| 서버가 특정 행을 거부 (형식 오류, 너무 긴 내용 등) | 범인 행을 찾아 **격리**한다(코드의 `bad`, `rejected`). outbox에서만 빼고 로컬 데이터는 그대로 둔다. 그 항목을 다시 고치면 재시도된다 | `error` "저장 못 한 항목 N개 — 이유" |
| 부모가 없는 노드가 생김 | 루트 아래로 옮긴다 | "복구된 노드 N개를 루트 아래 두었습니다" 토스트 |
| 커서가 너무 오래됨 (410) | 처음부터 전부 다시 받는다. 이 기기에만 있는 트리는 서버로 올린다 | 올린 트리가 있으면 토스트 |

보류와 격리는 "이 기기에는 있지만 서버에는 없는 데이터"가 생긴다는 뜻이다. `error` 상태를 방치하면 그 데이터는 다른 기기에서 보이지 않는다.

### 서버가 진실인 값이 전파되는 방식

공개 범위, slug, 관리자 숨김은 LWW를 타지 않는다.

- 서버는 이 값을 바꿀 때 수정 시각은 그대로 두고 `seq`만 올린다. 그래서 다른 기기가 pull로 받아 간다.
- 브라우저는 로컬 트리가 LWW에서 이기는 상황이어도 이 세 값만은 서버 값으로 덮는다.
- 브라우저가 push에 이 값을 담아 보내도 서버는 버린다.

## 8. 서버

### 구성

- 프레임워크는 **Hono**(가벼운 웹 서버 라이브러리)다.
- **빌드 단계가 없다.** Node 24가 TypeScript 파일을 직접 실행한다 (`node server/index.ts`). 이 방식 때문에 서버 코드에는 제약이 있다. import 경로에 `.ts` 확장자를 써야 하고, 타입은 `import type`으로 가져와야 하고, `enum`처럼 실행 코드를 만들어 내는 TypeScript 문법은 쓸 수 없다.
- DB는 **SQLite**다. 별도 패키지 없이 Node에 내장된 `node:sqlite`를 쓴다. ORM 없이 SQL을 직접 쓴다.

### 요청 하나가 지나가는 순서

`server/index.ts`의 `createApp()`이 이 순서로 조립한다. 순서가 곧 동작이다.

1. **요청 기록**: `/api/`와 `/t/` 요청에 대해 시각, 메서드, 경로, 상태 코드, 걸린 시간만 남긴다. IP와 브라우저 정보는 남기지 않는다.
2. **오류 형식 통일**: 모든 오류는 `{ error: { code, message, field? } }` 모양으로 나간다.
3. **세션 확인** (`/api/*`만): 쿠키로 사용자를 찾는다.
4. **위조 요청(CSRF) 차단**: 데이터를 바꾸는 `/api/*` 요청은 같은 출처에서 온 JSON 요청만 받는다. 카카오가 서버끼리 부르는 웹훅 경로 하나만 예외다.
5. **점검 모드**: 켜져 있으면 관리자와 일부 경로를 빼고 503을 돌려준다.
6. **API 라우트**: 계정(`server/account/`), 그다음 동기화·공유(`server/sync/`).
7. **`/api/*` 나머지**: 404.
8. **`/t/<slug>`**: 공유 링크용 HTML. 제목과 미리보기 정보를 넣어 돌려준다.
9. **정적 파일**: `dist/`의 빌드 결과. 어디에도 해당하지 않으면 `index.html`을 돌려준다.

### 로그인 (OAuth)

Google과 카카오를 지원한다. 코드는 `server/account/oauth.ts`와 `session.ts`에 있다.

1. `/api/auth/<제공자>/start`: 임시 쿠키에 검증 값을 넣고 제공자 로그인 화면으로 보낸다.
2. 제공자가 `/api/auth/<제공자>/callback`으로 돌려보낸다. 검증 값을 확인하고 제공자에게서 프로필을 받는다.
3. `signIn()`이 사용자 행을 찾거나 만든다. 정지된 계정이면 거절하고, 탈퇴 유예 중이면 복구한다.
4. 세션을 만들고 `sid` 쿠키를 굽는다.

세션에 대해 알아 둘 것:

- 쿠키에는 무작위 값이 들어 있고, DB에는 그 값의 해시만 저장한다.
- 일반 사용자는 쓰는 동안 30일씩 연장되고 최대 180일이다. **관리자 세션은 24시간이 상한이다.**
- 관리자는 `config/admins.json`(운영에서는 `/etc/drilldown/admins.json`) 목록으로 정한다. 로그인할 때마다 이 파일을 읽어 역할을 맞춘다.

**개발용 가짜 로그인.** 환경 변수 `AUTH_FAKE=1`일 때만 `/api/auth/fake/start`가 켜진다. 이 주소는 OAuth 없이 바로 로그인시키고, 주소에 `?as=admin`을 붙이면 **관리자 목록과 무관하게 관리자로 로그인된다.** 운영에서 이 값을 켜면 안 되는 이유다.

### 권한 확인

| 함수 | 있는 곳 | 실패 시 |
|---|---|---|
| `requireUser` | `server/http.ts` | 401 |
| `requireAdmin` | `server/http.ts` | **404.** 관리자 경로가 있다는 사실 자체를 숨긴다 |
| `ownTree` | `server/sync/share.ts` | 남의 트리이거나 없으면 404 |

### 요청 수 제한

`server/http.ts`의 `hit()`이 메모리에서 센다. `limit()`은 그것을 미들웨어로 감싼 것이다. 서버를 재시작하면 초기화된다.

누구의 요청인지는 로그인 사용자면 사용자 id로, 아니면 IP로 구분한다. IP는 Cloudflare가 넣어 주는 헤더(`cf-connecting-ip`)에서 읽는다. 경로별 한도는 각 라우트 등록 줄에 적혀 있다 (예: 동기화 분당 300회, 로그인 시작 분당 10회).

### DB

- 파일 위치는 `<DATA_DIR>/app.db`다. 개발 기본값은 `data/app.db`다.
- **마이그레이션**(스키마 변경 스크립트)은 서버가 시작할 때 자동으로 돈다. `server/migrations/`의 `NNN_이름.sql` 중 아직 적용하지 않은 번호를 순서대로 실행한다. 적용한 번호는 SQLite 파일에 기록해 둔다. 이미 데이터가 있는 DB라면 실행 전에 사본(`pre-migrate-NNN.db`)을 하나 남기고, 다음 정상 시작 때 지운다.
- 스키마를 바꾸려면 **기존 파일을 고치지 말고 다음 번호의 새 파일을 추가**해야 한다.
- 여러 SQL을 한 묶음으로 실행할 때는 `server/db.ts`의 `tx(db, fn)`을 쓴다. 중첩해서 쓸 수 없다.
- 시각은 전부 밀리초 정수다.

테이블 요약은 [4장의 대응표](#저장소-두-곳의-테이블-대응)에 있다. 컬럼 전체는 SQL 파일 두 개(합쳐 약 120줄)를 직접 읽는 것이 가장 정확하다.

### 보안 장치 한눈에

흩어져 있는 장치를 모았다.

| 위험 | 장치 | 있는 곳 |
|---|---|---|
| 내용에 스크립트를 심기 | 내용은 일반 텍스트로만 저장하고, 그릴 때 `<`, `>`, `&`를 바꾼다 | `features/editor/content/` |
| 다른 사이트가 사용자 대신 요청 보내기 | 같은 출처의 JSON 요청만 받는다 | `server/index.ts` |
| 세션 값 유출 | DB에는 해시만 저장. 쿠키는 스크립트에서 읽을 수 없게 설정 | `server/account/session.ts` |
| 관리자 경로 탐색 | 관리자가 아니면 404 | `server/http.ts` |
| 남의 트리 접근 | 소유자가 아니면 404 | `server/sync/share.ts` |
| 과도한 요청 | 경로별 요청 수 제한 | `server/http.ts` |
| 개인정보 기록 | 요청 기록과 DB에 IP·브라우저 원문을 남기지 않는다 | `server/index.ts`, `session.ts` |
| 로그인 후 엉뚱한 곳으로 보내기 | 돌아갈 주소는 `#/`로 시작하는 것만 허용 | `server/account/oauth.ts`, `core/me.ts` |

## 10. 공용 부품과 디자인 규칙

### 화면들이 같이 쓰는 것

| 파일 | 역할 |
|---|---|
| `features/Toast.tsx` | 토스트(잠깐 뜨는 알림). `toast(글, 버튼?, 시간)`과 한 번만 뜨는 `hint(id, 글)`. 한 번에 하나만 보이고 나머지는 줄을 선다 |
| `features/TreeHeader.tsx` | 트리 화면 네 개의 공통 머리. 제목과 모드 탭 |

| `features/feel.ts` | `haptic()`. 진동 피드백 |
| `ui/Sheet.tsx` | 시트: 아래에서 올라오는 대화 상자 |
| `ui/TwoStep.tsx` | 한 번 더 눌러야 실행되는 버튼 (탈퇴 등 위험한 동작용) |
| `ui/Tooltip.tsx` | 툴팁. 쓰는 쪽은 요소에 `data-tip="글"`만 붙이면 된다 |
| `ui/Icon.tsx`, `icons.ts`, `icons.all.ts` | 아이콘 |
| `ui/NodePath.tsx` | 루트부터 현재 노드까지의 경로 표시 |
| `ui/Avatar.tsx` | 프로필 그림. 없으면 이름 첫 글자 |
| `ui/theme.ts`, `ThemeToggle.tsx` | 라이트/다크 전환 |

### 디자인 규칙

UI 라이브러리와 CSS 프레임워크를 쓰지 않는다. 규칙은 `src/index.css`와 `docs/specs/01_design_system.md`에 있다.

- **색**: 무채색에 초록(`--ok`)과 빨강(`--danger`)만 쓴다. 강조용 파란색은 없다.
- **형태**: 모서리 반경은 2px 이하. 그림자와 반투명 흐림 효과는 쓰지 않는다. 떠 있는 요소는 1px 테두리로 표현한다.
- **테마**: 라이트와 다크 두 가지. `<html data-theme="...">`로 전환하고, 저장값이 없으면 시스템 설정을 따른다.
- **토큰**: 색, 크기, 시간 값을 `index.css`의 `:root`에 CSS 변수로 모아 둔 것. 각 CSS 파일은 값을 직접 쓰지 않고 이 변수만 쓰는 것이 규칙이다.
- **CSS 파일**: 기능 폴더마다 한두 개 있고 화면 파일이 직접 불러온다. 둘로 나뉜 곳은 첫 화면에 필요한 부분만 따로 떼어 낸 것이다 (예: `share-list.css`, `nav-user.css`, `treelist.css`).
- **클래스 이름**: 기능 이름을 앞에 붙인다 (`flash-*`, `dnd-*`, `share-*`). 상태는 클래스보다 속성(`data-result`, `aria-pressed` 등)으로 표현한다.
- **아이콘**: Lucide 아이콘의 SVG 내용을 문자열로 넣어 둔 것이다. 파일이 둘인 이유는 첫 화면을 가볍게 하기 위해서다. `icons.ts`는 첫 화면이 쓰는 것만, `icons.all.ts`는 나머지다.
- **색 외의 단서**: 색만으로 구분하지 않는다. 채점 결과와 숙련도에는 ✓, ✕ 기호를 함께 쓴다.
- **모바일**: 터치 기기에서는 누르는 영역을 44px 이상으로 한다. 입력칸 글자는 16px 이상이다. iOS가 작은 글자의 입력칸에 포커스하면 화면을 확대해 버리기 때문이다.

## 11. 기술 스택과 실행 방법

### 스택

| 구분 | 쓰는 것 | 용도 |
|---|---|---|
| 언어 | TypeScript 7 | 클라이언트와 서버 공통. 타입 검사 전용이고 파일을 만들어 내지 않는다 |
| UI | React 19 | 화면 |
| 번들러 | Vite 8 | 개발 서버와 빌드 |
| 로컬 저장 | Dexie 4 | IndexedDB를 쓰기 쉽게 감싼 라이브러리 |
| 간격 반복 | ts-fsrs 6 | FSRS 알고리즘 |
| PWA | vite-plugin-pwa | 서비스 워커와 manifest 생성 |
| 서버 | Hono 4 + @hono/node-server | HTTP |
| 서버 DB | `node:sqlite` (Node 내장) | SQLite |
| 린트 | oxlint | 코드 규칙 검사 |
| 점검 실행 | tsx | 클라이언트 `*.check.ts` 실행 |
| 통합 테스트 | Playwright | 브라우저 자동 조작 |
| 런타임 | Node 24.19 이상 25 미만 | |

실행에 필요한 의존성은 6개뿐이다 (react, react-dom, dexie, ts-fsrs, hono, @hono/node-server).

**쓰지 않는 것**: 상태 관리 라이브러리, 라우터 라이브러리, UI 컴포넌트 라이브러리, CSS 프레임워크, ORM, 단위 테스트 프레임워크. 전부 직접 만들었거나 브라우저와 Node의 기본 기능으로 해결했다.

**PWA 설정** (`vite.config.ts`): 서비스 워커는 새 버전이 나오면 자동으로 갱신된다. 관리자 화면 코드와 폰트는 미리 저장하는 대상에서 뺐다. `/api`와 `/t/` 주소는 서비스 워커가 가로채지 않는다.

### 명령어

| 명령 | 하는 일 | 언제 쓰나 |
|---|---|---|
| `npm run dev` | 클라이언트 개발 서버 (5173 포트). `/api` 요청은 3000 포트로 넘긴다 | 화면 개발 |
| `npm run dev:server` | API 서버. 파일이 바뀌면 재시작 (3000 포트) | 서버 개발 |
| `npm run build` | 타입 검사 후 `dist/` 생성 | 배포 전 |
| `npm run server` | 서버 실행. `dist/`와 API를 한 프로세스로 내보낸다 | 운영, 빌드 결과 확인 |
| `npm run typecheck` | 클라이언트와 서버 타입 검사 | 수정 후 |
| `npm run lint` | oxlint | 수정 후 |
| `npm run check` | 자가 점검 스크립트 전부 (브라우저 불필요) | 로직 수정 후 |
| `npm run e2e` | 빌드, 서버 기동, 브라우저 테스트까지 스스로 한다 | 통합 확인 |

### 처음 실행하기

1. Node 24.19 이상을 설치하고 `C:\drilldown\app`에서 `npm ci`를 실행한다.
2. **화면만 볼 때**: `npm run dev`를 실행하고 `http://localhost:5173`을 연다. 로그인 없이 트리 편집과 학습이 된다.
3. **로그인·동기화·공유까지 볼 때**:
   - `.env.example`을 `.env`로 복사한다. (`AUTH_FAKE=1`이 들어 있어 개발용 로그인이 켜진다.)
   - 터미널 하나에서 `npm run dev:server`, 다른 하나에서 `npm run dev`를 실행한다.
   - `http://localhost:5173`을 열고 로그인 화면으로 가면 "개발용 로그인" 링크가 있다.
4. **운영과 같은 모양으로 볼 때**: `npm run build` 후 `npm run server`를 실행하고 `http://localhost:3000`을 연다.

### TypeScript 설정이 네 개인 이유

실행 환경이 셋이라서다.

| 파일 | 대상 |
|---|---|
| `tsconfig.json` | 아래 둘을 묶는 껍데기 |
| `tsconfig.app.json` | `src/` (브라우저) |
| `tsconfig.node.json` | `vite.config.ts` (빌드 도구) |

`e2e/`와 `playwright.config.ts`는 `tsconfig.server.json`에 들어 있어 `typecheck`가 함께 검사한다.

## 13. 배포와 운영

자세한 절차는 `docs/ops/runbook.md`와 `deploy/`에 있다. 여기는 그림만 잡는다.

```
인터넷 ──▶ Cloudflare ──(Tunnel)──▶ Raspberry Pi
                                     ├─ cloudflared (터널 프로그램)
                                     └─ Node 서버 (127.0.0.1:3000 에만 열림)
                                          └─ /var/lib/drilldown/app.db
```

- 서버는 바깥으로 포트를 열지 않는다. Cloudflare Tunnel이 유일한 입구다.
- 경로: 앱은 `/opt/drilldown`, 데이터는 `/var/lib/drilldown`, 비밀 값은 `/etc/drilldown/env`.
- systemd 유닛은 서버 하나와 타이머 둘(백업, 정리)이다.
- **새 버전 올리기** (절차서 기준): `git pull && npm ci && npm run build && sudo systemctl restart drilldown-server`. DB 마이그레이션은 시작할 때 자동으로 된다.
- 백업은 암호화해서 외부 저장소로 올리도록 설정할 수 있다. 복호화 열쇠는 서버에 두지 않는다. 복원 절차는 절차서에 있다.

> **빠진 고리.** 절차서는 서버에서 `git clone`과 `git pull`로 코드를 받는다고 쓰여 있다. 그런데 `app` 저장소에는 원격이 없다. 배포하려면 먼저 원격 저장소를 만들어 올려야 한다.

## 15. 함정과 낡은 정보

### 깨뜨리면 안 되는 규칙

| 규칙 | 이유 |
|---|---|
| 편집기에서 노드 객체의 필드를 직접 바꾸지 않는다 | 저장 대상과 재측정 대상을 "객체가 바뀌었는가"로 찾는다 ([6.2](#편집-한-번이-저장되기까지)) |
| 동기화할 데이터를 쓸 때는 같은 트랜잭션에서 `track()`을 부른다. 그 트랜잭션에는 `outbox`와 `meta` 테이블이 포함돼야 한다 | 빠뜨리면 그 변경이 서버로 올라가지 않는다. `repo.ts`의 기존 함수를 쓰면 자동으로 된다 |
| `repo.deleteNodes()`에는 하위 노드까지 직접 넣어 준다 | 함수가 자손을 찾아 주지 않는다 |
| 서버의 `tx()` 안에서 `tx()`를 또 부르지 않는다 | 중첩이 안 된다. `server/sync/owner.ts`의 함수들이 스스로 트랜잭션을 열지 않는 이유다 |
| 서버 코드가 `src/`에서 실행 값을 가져오는 것은 `CAP` 하나로 유지한다 | 서버는 Node가 파일을 직접 읽는다. 확장자 없는 import가 섞인 `src/` 파일을 가져오면 실행이 깨진다 |
| 서버 라우트의 등록 순서를 바꾸지 않는다 | 예: `/api/auth/fake/start`가 `/api/auth/:provider/start`보다 먼저 있어야 한다 |
| 기존 마이그레이션 파일을 고치지 않는다 | 이미 적용된 번호는 다시 실행되지 않는다 |
| 운영에서 `AUTH_FAKE`를 켜지 않는다 | 누구나 관리자로 로그인할 수 있게 된다 |
| 서버 3000 포트를 바깥에 직접 열지 않는다 | 비로그인 요청의 수 제한은 Cloudflare가 넣어 주는 IP 헤더를 믿는다. 직접 열면 헤더를 꾸며 제한을 피할 수 있다 |

### 알려진 한계

코드를 읽은 결론이다. 실행으로 확인하지는 않았다.

**데이터가 기대와 다르게 움직일 수 있는 것**

- **노드를 지웠다가 실행 취소하면 학습 기록도 돌아온다. 단, 같은 세션 안에서만.** 지운 학습 기록은 메모리에 보관하므로 새로 고친 뒤의 되돌리기는 노드만 되살린다.
- **오래 꺼져 있던 기기가 전체 재동기화(410)를 하면** 서버에 없는 로컬 트리 중 최근 7일 안에 고쳤거나 올릴 변경이 남은 것만 다시 올리고, 나머지는 로컬 휴지통으로 보낸다 ([7장 시나리오 3](#시나리오-3-트리를-지웠다)).
- **기기 시계에 기댄다.** 충돌 판정이 기기의 시각이다. 서버가 5분 넘게 앞선 시각은 깎지만, 그 안의 차이나 뒤로 틀어진 시계는 보정하지 않는다.
- **트리 제목의 기준은 루트 노드 제목이다.** 서버 push 와 클라이언트 pull 적용이 둘 다 트리 제목을 루트 노드 제목으로 맞춘다. 직접 API 로 다른 값을 넣어도 루트 제목으로 바뀐다.
- **형제 정렬은 어디서나 `byOrder`(`core/path.ts`, `(order, id)`)다.** 직접 `a.order - b.order`로 정렬하지 않는다. 중간 삽입이 이웃 사이에 들어갈 수 없으면 형제를 0..n으로 다시 번호 매긴다.
- **같은 브라우저의 다른 탭 변경은 자동으로 반영되지 않는다.**

**규모와 흔적**

- **편집기는 보이는 카드를 전부 화면 요소로 만든다.** 큰 트리에서는 보기 깊이로 줄이는 것 말고 방법이 없다.
- **`events` 테이블은 180일이 지난 행을 지운다** (트리 목록이 열릴 때 `purgeDeletedTrees`).
- **`attempts` 테이블에 기록하는 코드가 없다.** 타입, 테이블, 동기화 경로만 있다.
- **초기 설계의 흔적이 일부 남아 있다.** 처음에는 답을 타이핑하는 학습 방식이었다. 쓰지 않는 함수(`isBranchComplete`, `nextConcept`, 재확인 분기)는 지웠지만, 서버가 검증하는 저장 필드(`GradeSource`의 `alias`·`fuzzy`·`self_*` 값, `pendingRecheck`)와 사용자가 편집하는 별칭은 남겼다.

| 세션 | 로그인한 상태를 서버가 기억하는 단위 |
| CSRF | 다른 사이트가 사용자 몰래 요청을 보내게 하는 공격 |
| 마이그레이션 | DB 스키마를 바꾸는 스크립트 |
| Hono | 가벼운 웹 서버 라이브러리 |
| OG 태그 | 링크를 메신저에 붙였을 때 나오는 미리보기 정보 |
| PWA | 설치해서 앱처럼 쓸 수 있는 웹앱 |
| 서비스 워커 | 브라우저가 뒤에서 돌리는 스크립트. 오프라인에서도 앱이 열리게 한다 |
| systemd | 리눅스에서 프로그램을 띄우고 예약 실행하는 장치 |
| Cloudflare Tunnel | 포트를 열지 않고 서버를 인터넷에 연결하는 서비스 |
| git worktree | 한 저장소에서 여러 브랜치를 각각 다른 폴더에 펼쳐 두는 기능 |
