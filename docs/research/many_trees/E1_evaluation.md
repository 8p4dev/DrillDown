# E1 — 해결안 교차 평가·우선순위 (2026-11-08)

작성 E1(평가자). 입력은 `R1_list.md`~`R7_share.md` 7개(문제 111개), 스펙 `00_overview.md` §4·§6(D1~D19), `04_tree_sharing_sync.md` §3.4·§3.10·§6. 이 평가에서는 앱을 실행하지 않았다. 사실 판단은 워커가 실측한 값과 코드 위치에 기대고, 아래 몇 가지만 직접 다시 확인했다: `src/router.ts:26-29`(편집 라우트도 `rootId`를 파싱함), `src/App.tsx:94`(에디터에만 `rootId`를 넘기지 않음), `src/core/srs/index.ts:7`(`DefaultScheduler()`를 인자 없이 호출), `src/features/editor/TreeListPage.tsx:38,80`(`purgeDeletedTrees` 호출 위치).
원 ID가 R3·R5에서 둘 다 `P1…`이라 이 문서에서는 **`R3-P*`/`R5-P*`** 로 구분해 적는다.

## 요약
1. 문제 111개를 사용자 경험 단위로 합치니 **61개(U01~U61)** 가 됐다. 그중 **P0은 7개**(S 7개)다. 데이터가 망가지거나 사라지는 동기화 결함 3개(U01 구조 손상·U02 200개 한도 정체·U07 조용한 미반영), 휴지통 무력화(U03), 백업에 트리 없음(U04), 키보드 Tab 트랩(U49), 빈 채점 221개 Again(U35). P0은 모두 몇 줄~수십 줄 수정이다.
2. 해결안은 공통 기반 5개로 대부분 묶인다. **(T1) 이미 있는 `?root=` 범위를 에디터와 진입점에 노출**하면 편집·학습·공유의 범위 문제(U14·U30·S2)가 한 메커니즘으로 풀린다. **(T2) 플래시의 경로 nav를 공용 컴포넌트로 꺼내면** 복습 맥락·에디터 위치·동명 노드·범위 라벨(U32·U15·U31·U36)이 함께 풀린다. **(T3) 레벨 접기는 `collapsed`를 쓰지 말고 '보기 깊이'로** 구현해야 한다. 그래야 R2·R5·R6이 서로 막아 둔 안들(접기 동기화 폭주·초기 깊이 제한)이 충돌 없이 함께 들어간다. 반면 "개요(목록) 모드 하나로 R2·R6·R7을 푼다"는 기각했다. 공유 보기는 이미 목록이라 `<details>`로 충분하고, 편집 화면을 두 벌로 만드는 비용이 크다.
3. 워커 평가 가운데 반대하는 것은 8건이다. 중간 노드 평가 제외(R3-P12)는 개념 회상을 없앤다. 정렬 4종 선택기(R1-L6)는 '최근 사용' 정렬 하나로 충분하다. 붙여넣기 미리보기 단계(R4-A10)는 붙인 뒤 되돌리기 토스트로 대신한다. 서브트리 미니맵(R3-P14)은 숨기면 된다. 레벨 접기를 `collapsed`에 쓰는 방식(R2-E7)은 위 T3로 바꾼다. 트리 간 이동(R4-A5)은 M보다 위험이 크다. 심각도 2건은 내렸다: R2-E1·R3-P5를 '치명'에서 '높음'으로(데이터 손실이나 사용 불가가 아님). 사용자 결정이 필요한 것은 10건이다(§6).

### T1. 서브트리 범위 `?root=` 하나로 편집·학습·공유를 통일
- **사실**: 라우터는 편집 라우트에서도 `rootId`를 파싱한다(`src/router.ts:26-29`). 플래시·빈칸·백지·공유 보기는 이미 이 값을 받아 쓴다. 넘기지 않는 곳은 에디터 하나뿐이다(`src/App.tsx:94`). `layout()`도 rootId 인자를 받는다(`layout.ts:21`, R2).
- **질문 "서브트리 포커스가 편집·학습·공유 범위 문제를 한꺼번에 푸는가"에 대한 답**: **범위 문제는 그렇다. 전체 조망 문제는 아니다.**
  - 편집: U14는 직접 해결된다. U13은 '한 가지 편집'이라는 사용 방식에서는 해결된다(폰에서 깊이 2 섹션 약 25노드 = 1~2화면, R6). U23 폰 편집도 화면이 작아져 쉬워진다.
  - 학습: 에디터 모드 탭(`TreeHeader`)이 현재 `?root=`를 그대로 넘기면, **포커스한 가지 = 학습 범위**가 별도 UI 없이 성립한다. U30의 '범위 진입점'은 이것으로 해결된다. 플래시 범위 선택기·기본값 임계(R3-P1·P2)는 목록에서 바로 들어오는 경로를 위해 여전히 필요하다.
  - 공유: S2(U30)는 공유 보기의 `<details>` 요약 옆에 `href.shared(slug, mode, node.id)` 링크를 다는 것이다. 같은 메커니즘이다.
  - 분리·내보내기: 포커스 상태에서 '이 가지 내보내기'는 `nodesToOutline(nodes, rootId, true)` 한 줄이다(U26 일부, R4-A6).
  - **풀지 못하는 것**: 트리 전체를 한눈에 보는 일(U13의 조망). 이것은 T3(보기 깊이)와 레이아웃 변경이 맡는다.
- **경계 규칙(필수)**: 포커스 루트에서는 삭제와 Shift+Tab을 막고, 붙여넣기는 포커스 안에서만 허용한다(R2·R6이 같은 지적).

### T3. '보기 깊이'를 `collapsed`와 분리
- **충돌**: R2-E7(레벨 접기)은 노드 수십 개의 `collapsed`를 한 번에 바꾼다. 이 필드는 동기화되므로(E15) outbox 폭주와 기기 간 덮어쓰기가 생긴다. R6은 바로 이 이유로 '폰 진입 시 깊이 2만 펼침'(M3-②)을 기각했다. R5-P7(1,000노드 초과 시 깊이 3까지만 펼침)도 같은 벽에 부딪힌다.
- **E1 안**: 레벨 접기를 `collapsed`에 쓰지 않는다. 에디터 로컬 상태 `viewDepth`(n 또는 ∞)를 두고 `layout`/`visibleRows`가 깊이 n을 넘는 노드를 숨기게 한다. 숨긴 하위 수는 배지가 이미 보여 준다. 데이터 계약을 바꾸지 않고, undo 대상도 아니며, 동기화도 일으키지 않는다.
- 효과: U17(73클릭 → 1번), 전체 조망(깊이 3에서 13카드, 46% 맞춤, R2 실측), R5-P7(큰 트리 초기 깊이 제한, P2), R6 M3-②(폰 진입 깊이 제한)가 **모두 같은 변수 하나로 들어간다.** 따라서 E15(접기를 보기 상태로 옮기는 마이그레이션, M)는 급하지 않아 P2로 남긴다.

### T4. 동기화 엔진 견고화 (P0 묶음)
U01·U02·U07·U08은 모두 `src/core/sync/engine.ts`와 `server/sync/push.ts`의 오류 처리 문제다. **한 PR**로 묶고 회귀 테스트도 하나로 한다(2기기, 500행 초과, 트리 201개, 노드 5,001개, 제목 250자). 구성:

### T5. 삭제 안전망

## 7. 이 평가의 한계
- 앱을 다시 실행하지 않았다. 실측값은 워커 보고서의 것이고, 코드 위치는 4곳만 다시 확인했다(머리말).

- R5-P11(저장소 퇴출)과 R6 스크린리더 항목은 실기기·실제 SR로 확인하지 않은 상태 그대로다.
