# R5 — 성능·저장 용량·동기화 (측정 중심)

작성 2026-11-08, 워커 R5. 코드 수정 없음. 표기: **[실측]** = 앱을 띄우고 Playwright(msedge, 1280×800, x64 Windows)로 측정한 것 / **[코드]** = 코드를 읽고 추론한 것 / **[추정]** = 측정하지 않은 가정.
측정 스크립트: 스크래치 `r5/perf.cjs`(목록·에디터·업로드·pull·한도), `r5/algo.ts`(레이아웃·트리 연산), `r5/orph.mjs`(서버 DB 구조 검사). 서버 `PORT=4305 DATA_DIR=.research-data/R5 AUTH_FAKE=1`, 측정 후 종료.

## 요약
1. **치명**: 계정 행이 500개를 넘으면 새 기기의 첫 동기화가 트리 구조를 **영구적으로 망가뜨린다**. 부모보다 먼저 도착한 자식을 "고아"로 보고 루트 밑으로 옮긴 뒤 서버에 다시 올리기 때문이다. 200트리로 실측해 보니 49개 트리, 2,600개 넘는 노드가 루트 밑으로 이동했고 서버까지 오염됐다.
2. 트리 개수가 늘어나도 **화면은 버틴다**. 200트리일 때 목록 첫 렌더 209ms, 복습 배지 8ms다. 무너지는 곳은 **동기화**다. 60/분 레이트 리밋에 걸려 업로드에 4분 넘게 걸리고 그동안 빨간 "동기화 오류"가 떠 있다. 받는 중에는 "저장됨"으로 표시된다. 201번째 트리를 만들면 **모든 동기화가 멈춘다**.
3. 노드 수가 늘면 에디터가 1000노드까지는 쓸 만하다(열기 0.6s, 키 입력 최대 72ms). **5000노드**에서는 열기 2.7s 동안 화면이 최대 1.9s 얼고, 키 하나에 최대 600ms가 걸린다. 매 렌더마다 모든 카드를 다시 재는 것이 원인이고, 레이아웃 계산 자체는 4.8ms로 싸다.

## 이미 잘 되는 것 (재확인)
- **트리 200개 목록**: 첫 렌더 209ms, DOM 13.6k, 힙 7.5MB [실측]. 트리 개수만으로는 목록 성능 문제가 없다(찾기·정렬 같은 불편은 R1 소관).
- **복습 배지(countDue)**: `srs.due` 인덱스 범위 조회라 200트리에서 8ms [실측]. 라우트를 바꿀 때마다 다시 세도 부담 없음.
- **Dexie 주 경로에 전체 스캔 없음**: 에디터 `nodes.treeId`, 플래시 `srs.treeId`, 배지 `srs.due` 모두 인덱스 [코드·실측].
- **레이아웃 계산**: 5000노드 4.8ms, 형제 4999개 19.5ms [실측]. 병목은 DOM 측정과 렌더다.
- **서버 처리**: push 500행 중앙값 58ms, pull 페이지 8ms(x64) [실측]. 200트리 SQLite 18.8MB.
- **pull 중 목록**: 트리 행이 먼저 오도록 seq 순서라 3초에 카드 200개가 보인다 [실측].
- **잘못된 행 1개가 큐 전체를 막지 않음**: 400은 이분 격리가 동작한다(P5의 불일치와 별개로, 나머지 59,000여 행은 계속 올라감) [실측].
- **222노드 예시 트리**: 붙여넣기 0.2~0.3s, 열기 0.5s, 노드 추가 42ms, 키 입력 40ms 이하 [실측]. 사용자의 실제 트리 크기에서는 성능 문제가 없다.
