# E2 — 치명·높음 주장 반대 검증 (2026-11-08)

작성 E2. 방법: R1~R7 문제 표에서 심각도 **치명·높음** 45건(원ID 기준)을 뽑아 각 코드 위치를 직접 읽고 반증을 시도했다. 핵심 5건은 포트 4310(`DATA_DIR=.research-data/E2`, 가짜 로그인 E2*)에서 API·Playwright(msedge)로 최소 재현했다. 재현 스크립트는 `.research-data/E2/p1.mjs`(P1 구조 손상)·`tl.mjs`(tree_limit 정체 + Tab 트랩)·`s2.mjs`(공유 범위 선택)에 남겼다. 서버는 끝나고 종료했다(PID 하나만).

## 확정된 데이터 손상 — 최소 수정안

### D1. R5-P1 첫 pull(또는 500행 넘는 pull)에서 페이지 경계 고아가 루트로 옮겨진 채 재push → 구조 영구 손상
- **재현**(`p1.mjs`): 기기 A가 API로 루트 1 + 중간 노드 300 + 각 중간 아래 잎 1(300)을 올리고, 중간 노드 300개의 제목만 고쳐 다시 올렸다. 이제 중간 노드 seq가 잎보다 뒤다. 새 브라우저 프로필(기기 B)로 로그인해 12초를 기다렸다. 서버에서 **잎 102개의 parentId가 루트로 바뀌었다**(나머지 198개는 정상). 102 = 첫 페이지 500행(트리 1·루트 1·잎 300·중간 198)에 부모가 안 들어온 잎 수와 정확히 같다.
- **원인**: `server/sync/pull.ts:13-25`는 seq 순으로 500행을 자른다. 노드를 고치면 seq가 새로 붙는다(`push.ts:112,116`). 그래서 **자식보다 나중에 고친 부모**는 뒤 페이지로 밀린다. 클라이언트 `applyRemote`는 페이지마다 고아 복구를 돈다(`src/core/sync/engine.ts:379-395`). 아직 안 온 부모를 "없는 부모"로 보고 노드를 루트 아래로 옮긴다. 이때 `updatedAt=now`를 붙이고 `track`(outbox)에 넣으므로, 이 값이 다음 push에서 LWW로 서버 원본을 이긴다. 원래 기기도 다음 pull에서 손상본을 받는다.
- **조건 재조정(보고서보다 넓음)**: 계정 pull 행(트리·노드·srs) 합이 500을 넘고, 어떤 부모 노드의 마지막 수정이 그 자식보다 나중인 경우다. 수정에는 제목·접기(`collapsed`)·위치(`offset`)·너비가 모두 들어간다. 평범한 편집(부모 이름 고치기, 접기)만으로 충족된다. 새 기기 첫 로그인, 커서 만료(410) 재스냅샷, 오래 꺼 둔 기기의 큰 증분 pull에서 터진다. **심각도: 치명 유지.**
- **최소 수정안**(`engine.ts`, 약 10줄): 고아 복구를 `applyRemote`에서 떼어 낸다. 같은 블록(379-395)을 `rescueOrphans(treeIds)`로 옮기는 것이다. 호출 지점은 두 곳이다. ① `applyRemote` 안에서는 `force=true`(push 응답 superseded)일 때만 호출한다. ② `pullFrom`은 페이지마다 `applyRemote`의 반환값(changed)을 누적하고, 루프가 `!r.more`로 끝난 **뒤 한 번만** 호출한다. 중간에 429·오프라인으로 끊기면 복구도 건너뛴다. 다음 pull이 커서부터 이어 받은 뒤에 한다. 그동안 부모 없는 노드가 잠깐 안 보일 수 있다. 에디터 레이아웃이 고아를 어떻게 그리는지는 확인하지 않았다.
- **회귀 체크 1개**: `.research-data/E2/p1.mjs`(서버 4310에 대해 `leavesUnderRoot === 0` 이면 통과). E2E로 옮긴다면 같은 시나리오를 `rows: 500` 대신 작은 `LIMITS.rows`로 돌려도 된다.

### D2. R1-L1/R5-P4 tree_limit 403이 outbox 전체를 멈춤
- **재현**(`tl.mjs`): API로 트리 200개를 올렸다. 새 프로필로 로그인하면 카드 200개가 보인다. 거기서 목록 입력칸으로 "201번째"를 만들었다. 그 뒤 기존 트리 t0에서 Tab으로 자식 "child"를 추가했다. 로컬 treeitem은 2개인데 **서버 t0 노드는 1개**였다. 상태는 `동기화 오류 · 트리가 너무 많습니다(200개)`로 고정됐다.
- **a05f8a5가 못 다루는 이유**: 격리 조건 `engine.ts:178`이 `413`, `400 invalid`, `400 payload_too_large`만 받는다. `403 tree_limit`은 그대로 throw된다. 게다가 `pushAll`이 outbox를 tree 먼저로 정렬한다(`engine.ts:125`). 그래서 새 트리 행이 매 배치 맨 앞에 들어가고, 서버는 행을 하나도 적용하기 전에 배치 전체를 거부한다(`push.ts:71-75`, 트랜잭션 맨 앞). 옛 트리 삭제도 같은 배치 뒤쪽에서 처리돼 상한 계산을 못 바꾼다. 403을 단순히 이분 격리 대상에 넣으면 새 트리 행 하나만 격리되고, 같은 배치에 있던 그 트리의 노드 행은 서버가 `dropped`로 돌려준다(`push.ts:110`). 그러면 outbox에서 지워져 **나중에 자리가 나도 노드가 안 올라간다**. 그래서 "격리"가 아니라 "보류"가 필요하다.
- **최소 수정안**(`engine.ts`, 약 8줄): 메모리에 `held = new Set<ID>()`를 둔다. `pushAll`에서 정렬한 뒤 `rows.filter(r => !held.has(r.treeId))`로 보류 트리를 건너뛴다. `pushOnce`의 catch에서 `e.code === 'tree_limit'`이면 slice에 있는 tree put 행의 treeId를 전부 `held`에 넣고 return한다. 어느 트리가 새것인지 클라이언트는 모르지만, 기존 트리 put은 다음 라운드에 그 트리를 빼고 다시 보내면 된다. 엄밀히 하려면 tree 행만 이분 탐색한다. `held`는 `start()`와 트리 삭제(`markTreeDeleted`) 때 비운다. 오류 문구는 기존 `fail` 문구를 그대로 `bad`에 넣어 계속 보이게 한다. 로그인 전 로컬 트리가 200개를 넘는 M1 병합 업로드도 같은 경로로 풀린다.
- **회귀 체크 1개**: `.research-data/E2/tl.mjs`에서 `serverNodesOfT0 === 2`(201번째 트리가 있어도 기존 트리 편집이 서버에 도달).
- **심각도: 치명 유지**(L1). 201번째는 로그인 사용자가 경고 없이 바로 밟는다. 정체가 길어지면 다른 기기 편집과 LWW로 섞이면서 손실이 생길 수 있다(추정).
