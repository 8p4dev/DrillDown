# R1 — 트리 목록 관리: 트리가 많아질 때의 문제·불편 (2026-11-08)

표기: **[실사용]** = 포트 4301 앱을 Edge(Playwright)로 실제 조작해 확인 · **[코드]** = 코드에서 추론(실행 확인 안 함) · **추정** = 근거 약함.
실험 데이터: 사용자 예시 트리(개요 붙여넣기 → 노드 222) 1개 + 비슷한 이름 트리 205개를 목록 입력칸으로 하나씩 생성(`네트워크`, `네트워크 보안`, `네트워크 기반 공격 기출`, `… 사본` 등 15과목 × 14접미사). 1440×900, 390×844(모바일) 두 폭. 스크립트는 스크래치(`r1/p1~p9.mjs`), 데이터 `.research-data/R1/`.

## 요약
1. **데이터가 사라지거나 되살릴 수 없는 결함 3개가 목록에서 실제로 재현됐다**: ① 200개 한도를 넘기면 동기화 큐 전체가 멈추고, 옛 트리를 지워도 풀리지 않는다(다른 트리 수정·삭제도 서버에 안 감) ② 휴지통(7일)은 삭제 후 10초가 지나면 항상 비어 있다 — 서버엔 7일 남아 있는데 사용자가 복구할 길이 없다 ③ 연속 삭제 시 두 번째 이후 "되돌리기"는 눌러도 아무 일도 없다.
2. **찾기 도구가 전혀 없다**: 검색·정렬·필터·폴더·태그 없음, 순서는 "마지막 편집" 고정. 206개일 때 PC 9,177px·모바일 28,399px를 스크롤해야 하고, 예시 트리는 맨 아래(206번째)로 밀려났다. 카드에 노드 수·복습 due·최근 학습이 없어 '네트워크'류 43개를 이름만으로 구분해야 한다(아바타도 전부 '네').
3. 가장 값싼 해결은 **목록 위 검색 입력 1개 + 카드 한 줄 메타(노드 수·due)** 와 **결함 3개의 국소 수정**이다. 폴더/태그·가상 스크롤·대량 선택은 지금 규모(≤200)에선 보류를 권한다.
